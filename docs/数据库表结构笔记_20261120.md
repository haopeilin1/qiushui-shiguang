# 基础表：项目的"实体"们

一共 **6 张主表 + 4 张权限表**（原口径 4 张主表，补上 `t_channel` / `t_channel_topic_rel` 后为 6 张）。
先建立一个总的印象：基础表的删除几乎全是"**逻辑删**"——做标记、不删行。记住这一点，后面和事实表对比时会用得上。

## 1. t_user 用户表（一切的起点）

关键字段：`id`（主键）、`phone`（登录账号，唯一）、`password`（BCrypt 加密存储）、`nickname`/`avatar`/`introduction`、`status`（0 正常 / 1 禁用）、`is_deleted`（逻辑删标记）

**为什么注销不真删？** 因为用户发的笔记、评论还得显示（通常显示"用户已注销"），点赞关系、计数也都引用了这个 `user_id`——真删了，满世界都是悬空引用。这就是逻辑删存在的理由：**有人引用你，你就不能物理消失。**

> 补注（与脚本对齐）：实际唯一索引是 `uk_phone (phone, is_deleted)`，不是 `phone` 单列。
> 这样"注销后同手机号重新注册"能共存；代价是同一手机号只能有一条已删除记录。

## 2. t_note 笔记表（内容本体）

关键字段：`id`（雪花 ID，主键）、`creator_id`（作者）、`title`、`img_uris`、`visible`（0 公开 / 1 仅自己）、`status`（0 正常 / 1 删除）、`content_uuid`（正文钥匙）

这张表最重要的设计：**元数据与正文分离。** 元数据（标题、作者、图片地址）小且结构固定，存 MySQL；正文是大段文本，存 Cassandra。好处：MySQL 的行小而整齐，列表查询（一次查几十篇的元数据）飞快；正文只在打开详情时才按 `content_uuid` 单独取。

> 补注：表里还有一个 `topic_name` 冗余字段——这是"只存 ID 不冗余"原则的**有意例外**：
> 话题名几乎不变，冗余一份可以避免每次列表都去 join/远程查；而昵称头像会频繁变，所以坚决不冗余。

## 3. t_announcement 公告表（我们新增，结构最朴素）

关键字段：`id`（雪花）、`title`、`content`、`creator_id`（发布人）、`status`（0 生效 / 1 撤回）

注意它连 `is_deleted` 都没有，用 `status` 一个字段管生命周期。

## 4. t_topic 话题表（最简单的配角）

关键字段：`id`、`name`（唯一）

事件就两个：发笔记选了新话题 → 增；发笔记/浏览时 → 查。没有删改。
实际唯一索引是 `uk_name (name, is_deleted)`，和 `t_user.uk_phone` 是同一个套路。

## 5. t_channel 频道表（比话题更大的一层分类）

关键字段：`id`（主键）、`name`（频道名）、`create_time`、`update_time`、`is_deleted`（逻辑删标记）

**先说定位**：频道是"比话题更大的一层分类"。

- **话题**（`t_topic`）是用户发笔记时自己选的（#穿搭、#春节），用户产生、数量多；
- **频道**是运营侧配置的栏目（"穿搭"、"美食"、"职场"），运营维护、数量少、几乎不变；
- 一个频道下可以挂多个话题，一个话题也可以出现在多个频道里——这层多对多关系落在下一张 `t_channel_topic_rel`。

**代码现状（这点面试必须说准）**：`t_channel` 目前只有 MyBatis Generator 生成的
`ChannelDO` / `ChannelDOMapper` / `ChannelDOMapper.xml`，**业务代码还没有任何调用**，属于**预留能力**。
所以别把它说成"已上线的频道功能"，说"预留的频道-话题分层模型"更稳——面试官真去搜 `channelDOMapper.`
是搜不到调用点的。

**为什么单独建表，而不是在 `t_topic` 里加个频道字段**：

- 频道是"运营配置"，**读多写少**、几乎不改，和用户产生的话题生命周期完全不同；
- 拆开后改频道名不影响话题，话题也能被多个频道复用（加字段只能一对一）。

**索引建议**：与 `t_topic` 保持一致，用 `uk_name (name, is_deleted)`。
（注意：当前 `sql/01_schema.sql` 里还没有这张表，属于待补 DDL。）

## 6. t_channel_topic_rel 频道-话题关系表

关键字段：`id`（主键）、`channel_id`（频道 ID）、`topic_id`（话题 ID）、`create_time`、`update_time`

一行 = "**某个频道包含某个话题**"，典型的多对多中间表。

**为什么需要中间表**：如果在 `t_topic` 里加一个 `channel_id` 字段，一个话题就只能属于一个频道；
但现实中"#春节"既可能挂在"生活"频道，也可能挂在"职场"频道。中间表把关系单独存，两个方向都能查：

- 频道页：`where channel_id = ?` → 这个频道下有哪些话题；
- 话题反查：`where topic_id = ?` → 这个话题被挂到了哪些频道。

**索引建议**：

- `UNIQUE KEY uk_channel_topic (channel_id, topic_id)`：防止同一话题在同一频道重复挂载；
- `KEY idx_topic_id (topic_id)`：支持"话题 → 频道"的反查。

**代码现状**：同样只有 `ChannelTopicRelDO` / `ChannelTopicRelDOMapper` / XML，业务代码未调用。
表名、字段与 DO 一一对应，补 DDL 时照抄即可。

## 7. RBAC 权限四表（`t_role` / `t_permission` / `t_user_role_rel` / `t_role_permission_rel`）

这四张是"**配置型**"基础表，特点和前面不同：**平时几乎不写，但每次请求都在读。**

怎么"沿链查"？校验"用户 10001 能不能发公告"的路径：

```
t_user_role_rel:        user_id=10001 → 他有哪些 role_id
       ↓
t_role_permission_rel:  这些 role_id → 挂哪些 permission_id
       ↓
t_permission:           permission_id → permission_key 里有没有 announcement:publish
```

三表连查，最后落到"有没有那个权限 key"——这就是 RBAC 在数据库层面的完整形态。

> 补注：`t_permission.type` 区分 1-菜单 / 2-按钮 / 3-接口，所以权限点粒度可以到**接口**，
> 这也是网关能按路由（而不是按页面）做校验的前提。
