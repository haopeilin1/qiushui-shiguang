## 第 0 步：前端发出请求

```
POST http://47.100.x.x:8000/note/note/publish
Authorization: Bearer f4a9c2e1b8d3...（张三的 Token）
Content-Type: application/json

{
  "type": 0,                    // 0=图文笔记，1=视频笔记
  "title": "我们部门的代码评审经验",
  "content": "分享一下我们团队坚持了两年的评审流程，第一……",
  "imgUris": ["http://minio/img/aaa.jpg", "http://minio/img/bbb.jpg"],
  "topicId": 5                  // 话题 ID，数字（BIGINT），不是文本
}
```

**请求头 `Authorization: Bearer <Token>` 逐词拆解**：

- HTTP 请求分**请求头**（元信息：你是谁、什么格式）和**请求体**（业务数据：标题、正文）。`Authorization` 是协议规定的标准凭证字段（Sa-Token 配置 `token-name: Authorization`）。
- **Token** 是张三登录那天 auth 服务签发的 128 位随机字符串（`token-style: random-128`），本质是**数字工牌**：登录时验证手机号+密码（这一刻查 MySQL），通过后在 **Redis** 里记下"这串字符 = 10001"，返回给前端。之后每个请求都带它。
- **Bearer**（持票人）是类型前缀，来自 OAuth2/JWT 惯例，含义是"谁持有这张票就信任谁"——所以 Token 泄露等于工牌被捡走，这就是它要有有效期、传输走 HTTPS 的原因。
- 时限：配置 `timeout: 2592000` = **30 天**，到期 Redis 记录自动销毁；主动退出登录也会立刻删除。`active-timeout: -1` 表示不启用活跃续期——**到点就死，用得再勤也不续命**。过期或退出后必须重新登录领新 Token。
- 地址里**两个 `/note` 不是笔误**，第 2 步解释。

## 第 1 步：Gateway 验票（每个请求都验，不是只在登录时）

请求先到 Gateway（8000 端口，唯一入口）。Sa-Token 全局过滤器（`SaTokenConfigure.java`，拦截 `/**`）做两层校验：

**第一层：登录校验（全员每请求必查）**
拿 Token 去 **Redis** 查（`AddUserId2HeaderFilter.java:61`）。注意：只查 Redis，永远不查 MySQL——Token 是登录会话，只活在 Redis；MySQL 存的是账户本体（手机号、密码哈希），只在登录那一刻用一次。查不到/过期 → 直接判定未登录，401 打回，没有"去 MySQL 找找"这回事。
白名单（不验票直接放行）：`/auth/login`、`/auth/verification/code/send`、用户主页、搜索热榜等公开接口。

**第二层：权限点校验（按路由点名，点到才查）**
项目里只有三条管理路由绑了权限点（我们的 RBAC 改造落点）：

```java
SaRouter.match("/note/announcement/publish",   r -> StpUtil.checkPermission("announcement:publish"));
SaRouter.match("/note/announcement/read/stat", r -> StpUtil.checkPermission("announcement:readstat"));
SaRouter.match("/note/announcement/withdraw",  r -> StpUtil.checkPermission("announcement:manage"));
```

**发笔记不在清单里**——发笔记是全员普通功能，登录即可。张三的请求过了第一层就继续走。

一句话：**登录校验 = 全员每请求必查；权限校验 = 按路由点名，点到名的才查角色权限。**

**身份换发**：过滤器把 userId 写入转发请求的请求头（`AddUserId2HeaderFilter.java:71`，header 名 = `GlobalConstants.USER_ID`）。

## 第 2 步：路由——按 URL 前缀决定去哪个服务

网关配置文件（`application.yml`）里的路由表：

```yaml
- id: note
  uri: lb://shiguang-note     # lb:// = 去 Nacos 找实例 + 负载均衡
  predicates:
    - Path=/note/**           # /note 开头 → 笔记服务
  filters:
    - StripPrefix=1           # 转发前剥掉第 1 段路径
```

`/note/note/publish` 匹配 `Path=/note/**`，`StripPrefix=1` 剥掉第一个 `/note`，**真正转发的是 `/note/publish`**。两个 note 的真相：**第一个给网关做路由匹配，第二个是笔记服务内部真实路径**。（对照：公告走 `/note/announcement/publish` → 剥一层 → `/announcement/publish`，正好匹配我们写的 AnnouncementController 的 `@RequestMapping("/announcement")`。）

## 第 3 步：Nacos 查址 + 负载均衡 + HTTP 转发

1. `lb://shiguang-note` → 网关拿服务名去 **Nacos** 查："这个服务有哪些活着的实例？" 返回如 `["192.168.1.10:8081", "192.168.1.11:8081"]`。
2. **负载均衡**挑一台（默认轮询：这次 10，下次 11）。
3. **转发形式 = 一次标准 HTTP 请求**：方法（POST）、路径（剥后的 `/note/publish`）、请求头（Authorization + 新写入的 userId）、JSON body 原样发过去。网关就是"反向代理 + 加工站"，不改数据格式。

## 第 4 步：note 服务接球——框架分发 + 身份入柜

**"框架触发方法"的含义**：Controller 方法从来不是你的代码调用的，是框架替你调的。链条：HTTP 报文到达 → 内嵌 Tomcat 解析（方法=POST、路径=/note/publish）→ Spring 总调度员 DispatcherServlet 查启动时扫注解建好的路由表 → 命中 `@RequestMapping("/note")` + `@PostMapping("/publish")` → **反序列化** JSON 为 `PublishNoteReqVO` → 调用 `publishNote(vo)`。**这就是"怎么知道是发布而不是修改"的全部机制**——URL 路径 + HTTP 方法精确匹配到不同方法，等价于框架帮你写了 `if (url.equals(...))`。
（类比：你是厨师只负责做菜，服务员=框架负责接单、看单子、端菜。机制名：Spring MVC 请求分发，DispatcherServlet + 注解路由。）

**身份入柜（context starter 第①件 `HeaderUserId2ContextFilter`）**：

```java
String userId = request.getHeader(GlobalConstants.USER_ID);  // 读头里的 10001
LoginUserContextHolder.setUserId(Long.valueOf(userId));      // 存入 ThreadLocal
try { chain.doFilter(request, response); }                   // 放行
finally { LoginUserContextHolder.remove(); }                 // 请求结束必须清空
```

**ThreadLocal = 每个线程的私人储物柜**：每个请求由一个线程处理（线程池复用），ThreadLocal 的值焊在线程上，线程之间互不可见。业务代码从此在任何地方 `getUserId()` 直接拿到 10001，**不用层层传参**。

**`finally` 里的 remove() 性命攸关**：线程池复用线程，不清空的话下一个请求复用这个线程会读到上一个用户的身份——**串号事故**（张三的请求看到李四），面试必问。

**为什么用 TransmittableThreadLocal 而不是普通 ThreadLocal**：笔记详情用 `CompletableFuture.supplyAsync` 并行聚合，任务会**换一个线程**执行——普通 ThreadLocal 焊在原线程上，新线程拿到 null（查"当前用户是否赞过"就会出错）。TTL（TransmittableThreadLocal，阿里开源）在任务提交时把上下文**打包随任务交接**给新线程，干完还原。

**跨服务续传（第③件 `FeignRequestInterceptor`）**：note 服务再用 Feign 调别的服务时，拦截器自动从柜子取 userId 写入新请求的请求头；下一个服务的过滤器再入柜。身份一站一站传下去——这就是简历上"Token 解析 → 请求头透传 → ThreadLocal 绑定 → Feign 续传"的完整真身。

```
Gateway：Token 换出 userId=10001，写入请求头
   │  HTTP（请求头带 userId）
   ▼
note 服务：过滤器读头 → setUserId 入柜 → 业务代码随手 getUserId()
   │  Feign 调用（拦截器自动把 userId 写入新请求头）
   ▼
user 服务：它的过滤器再入柜 → 它的业务代码也能 getUserId()
```

## 第 5 步：publishNote 主流程（NoteServiceImpl:112-219）

**⑤ 参数校验**（:128-146）：type 必须是 0/1；图文图片非空且 ≤8 张，拼成逗号分隔字符串 `"aaa.jpg,bbb.jpg"`；视频链接非空。

**⑥ 拿笔记 ID**（:148）：Feign 调 **ID 生成服务**（独立微服务，`DistributedIdGeneratorFeignApi.getSegmentId("leaf-segment-note-id")`）。它是全系统统一"发号器"（Leaf 号段模式：一次从库里领 1000~1999 一批号放内存慢慢发，发完再领，性能高），保证多台机器同时发笔记 ID 不重复。返回 `"1834567890123456"`。
⚠️ 细节：此时还没校验话题——代码顺序就是先领号再校验（:171 才查话题），话题不存在号就白领了。无害但可以说"先校验参数再领号更优"。

**⑦ 生成正文钥匙**（:160）：content 非空 → **本地** `UUID.randomUUID()` 生成 `contentUuid = "a1b2c3d4-..."`。此刻正文哪儿都没存（同步调 kv 的代码被注释掉了，:162-167）。

**⑧ 校验话题**（:171-176）：`SELECT name FROM t_topic WHERE id=5` → "职场干货"（不存在抛 `TOPIC_NOT_FOUND`）。t_note 同时存 `topic_id`（数字，关联用）和 `topic_name`（文本，**冗余**——列表页一次显示 20 篇的话题标签，不用 join 20 次话题表；代价是话题改名后旧笔记显示旧名，可接受）。

**⑨ 分支判断**：
- **正文为空** → 直接 `insert` t_note，返回成功（:202），不发事务消息；
- **有正文** → 进入事务消息流程（本例走这里）。

## 第 6 步：事务消息——半消息（:214）

`rocketMQTemplate.sendMessageInTransaction("PublishNoteTransactionTopic", message, null)`，消息体是 `PublishNoteDTO` 完整 16 字段 JSON（id、title、creatorId=10001、topicId=5、topicName、type=0、imgUris、status=0、contentUuid、**content 全文**……）。

**半消息**：MQ 持久化收下，但标记"暂存，不可消费"——像把快递单先押在快递柜，等发货信号。

**为什么不能直接插库再发消息？（两个崩溃窗口）**
- 先插库后发消息：插完宕机 → 消息永远没发 → Cassandra 永远没有正文 → 打开笔记正文 404，没人来补；
- 先发消息后插库：消息发了、库插失败 → 用户看到失败，但正文已落库成孤儿数据。
- try-catch 补偿没用：进程被 kill 时 catch 根本不执行。这和 Lua 的 check-then-act 是同一类病，只是跨了进程。

**事务消息的思路**：先把"要发消息"这件事**抵押在 MQ**（半消息持久化，笔记服务之后死不死纸条都在），再办数据库的事，最后凭结果裁决。

## 第 7 步：MQ 回调本地事务（PublishNote2DBLocalTransactionListener:48-108）

MQ 收到半消息后回调 note 服务的 `executeLocalTransaction`（**插入还是 note 服务自己的代码，MQ 不碰数据库**，它只提供"保管+催办"）：

- **a. 第①次删缓存**：`DEL published_note_list:10001`（直连 Redis，不走 MQ）。
  为什么删：这个缓存是"看出来的"——上次有人访问张三主页时系统查库顺手存的（key 用 userId，因为列表属于作者）。现在多了新笔记，旧列表里没有，删掉后下次访问缓存 miss → 回源重建自然带上新笔记。
- **b. 插库**：`INSERT INTO t_note`，新行内容：

| id | creator_id | title | topic_id | topic_name | type | img_uris | status | visible | content_uuid |
|---|---|---|---|---|---|---|---|---|---|
| 1834567890123456 | 10001 | 我们部门的代码评审经验 | 5 | 职场干货 | 0 | aaa.jpg,bbb.jpg | 0 | 0 | a1b2c3d4-... |

- **c. 裁决**：成功 → 返回 `COMMIT`，半消息转正；失败 → `ROLLBACK`，消息销毁，两边都不留脏数据。

**事务里顺手发两条消息**（:77-105）：
- **延迟消息**：`DelayDeletePublishedNoteListRedisCacheTopic`，负载就是 `"10001"`，延迟级别 1（=1 秒）——延迟双删的第②删的"闹钟"。为什么用 MQ 当闹钟而不自写定时器：**消息持久化在 MQ，进程重启不丢**；内存定时器重启就没了。
- **业务事件**：`NoteOperateTopic:Publish`，消息体 `NoteOperateMqDTO` 只有 3 个字段：`{creatorId:10001, noteId:1834567890123456, type:1}`。

**延迟双删防的并发漏洞**：第一次删缓存后，若有个在插库提交*之前*就开始的慢读请求，它读到旧列表、在删除*之后*回填缓存 → 缓存又脏了。1 秒后的第二次删除专门清这种漏网之鱼（1 秒 > 一次回源+回填的耗时）。

## 第 8 步：响应用户

`Response.success()` → `{"code":0,"message":"成功"}` → 网关 → 前端显示"发布成功"。

**张三的等待到此结束。用户等待的只有第 0~8 步；以下全是后台异步发生的。**

## 异步段（用户已看到"成功"）

**⑩ kv 服务存正文**：`SaveNoteContentConsumer` 消费转正消息 → 取出 contentUuid + content → Cassandra 执行 `INSERT INTO note_content (id, content)`。
- 消费机制：kv 启动时用 `@RocketMQMessageListener` 声明订阅，代码上是被动接收；底层是消费者**长轮询**（不断问 MQ"有我的消息吗"，挂起等待，有消息立刻返回），效果等于实时推送，延迟毫秒级。
- Cassandra 的 `note_content` 就两列：`id`(UUID) + `content`——**一个超大字典**。正文不混在 MySQL 的原因：一篇几十 KB，混在 t_note 里每次查列表都拖着大文本；拆开后 MySQL 行小查得快，正文只在打开详情时按 uuid 单独取。

**⑪ count 服务计数 +1**：`CountNotePublishConsumer` 消费 Publish 事件：
- **幂等前置**（我们加的组件）：`mqDedupSupport.isDuplicateByEvent(..., "PUBLISH:1834567890123456")`——同一篇笔记一生只发布一次，业务键天然唯一；
- **Redis**：`HINCRBY count:user:10001 note_total 1`——**前提 key 存在才更新**（计数缓存有 TTL，不常驻；不存在就跳过，等查询时回源重建。"缓存只服务正在被看的数据"）；
- **MySQL**：`t_user_count` 张三那行 `note_total +1`。
- 两处是同一份数据的两个副本：**MySQL 是持久真相，Redis 是读加速快照**，过期了从 MySQL 重新拍。

**⑫ 延迟双删第②删**：1 秒后 `DelayDeletePublishedNoteListRedisCacheConsumer`（note 服务自己的消费者）收到延迟消息 → 再次 `DEL published_note_list:10001`。**两次删除都是 note 服务干的，MQ 只当闹钟。**

**⑬ data-align 记待办**：`TodayNotePublishIncrementData2DBConsumer` 同样消费 Publish 事件，把 creatorId 记入当日临时表，夜间 XXL-JOB 对账校正发布数。

**⑭ 异常兜底·事务回查**：若 note 服务在半消息后宕机，MQ 超时主动回查 `checkLocalTransaction`：`SELECT count(*) FROM t_note WHERE id=1834567890123456`——**以数据库为准**：有这行 → COMMIT 转正；没有 → ROLLBACK 销毁。消息永远不悬空、不和数据库打架。

## 贯穿全文的通信观

跨进程**没有方法调用，只有发消息**。本文涉及的"接口"分四种：

| 形态 | 例子 | 调用方运行什么 | 被调用方何时执行 |
|---|---|---|---|
| HTTP | 前端 → Gateway → 服务 | 只发网络请求 | 对方进程的框架收到报文后触发处理逻辑 |
| Feign | note → ID 服务 | 代理对象的翻译逻辑（拼 URL、序列化、发 HTTP） | 对方 Controller 收到请求后执行 |
| MQ | note → RocketMQ | 把消息交给 MQ 就返回 | 消费者之后被 MQ 投递触发，与生产者完全脱节 |
| 命令/SQL | 各服务 → Redis/MySQL | 只发网络命令 | 数据库进程收到后执行 |

调用方/被调用方是相对的：Gateway 对前端是被调用方，对 note 服务又是调用方；每个进程收到报文后由**自己的框架**接管触发处理逻辑（Gateway 是过滤器链，note 服务是 Controller 方法）。
