> 整理日期：2026-11-20（终版，纳入校验代码重复性、MyBatis 边界、@Transactional 包裹范围等追问细节）
> 示例：**张三（userId=10001）删除自己的笔记（id=1834567890123456）。**
> 代码：`NoteServiceImpl.deleteNote`（:581-649，`@Transactional(rollbackFor = Exception.class)`）
> 勘误：逻辑删 status = **2**（枚举 `NoteStatusEnum`：NORMAL(1)、DELETED(2)、DOWNED(3)）；建表注释"0-正常 1-删除"已过时，以代码为准。

## 第 0 步：前端发请求

```
POST http://47.100.x.x:8000/note/note/delete
Authorization: Bearer f4a9c2e1...（张三的 Token）
Body: { "id": 1834567890123456 }     // DeleteNoteReqVO 只有一个字段
```

入口段与发布/修改完全一致（验票 → userId 透传 → 路由 → 剥前缀 → Nacos → 负载均衡 → 身份入柜 → Spring 分发到 `deleteNote()`）。

## 第 1 步：存在性 + 归属校验（:586-597）

```java
NoteDO selectNoteDO = noteDOMapper.selectByPrimaryKey(noteId);
if (Objects.isNull(selectNoteDO))      throw new BizException(NOTE_NOT_FOUND);
Long currUserId = LoginUserContextHolder.getUserId();
if (!Objects.equals(currUserId, selectNoteDO.getCreatorId()))
                                       throw new BizException(NOTE_CANT_OPERATE);
```

每行背后：
1. `selectByPrimaryKey`：MyBatis 代理按方法名找到 XML 的 SQL → `#{id}` 预编译填参（防注入）→ MySQL 主键索引直接定位（最快查询）→ 结果集每列映射成 NoteDO 字段返回；
2. 判空抛异常：方法中断，全局异常处理器转成统一错误响应；`@Transactional` 同时回滚（此时无写入，无实际影响）；
3. `getUserId()`：从当前线程 ThreadLocal 取 10001，无参数无查询；
4. `Objects.equals`：纯内存比较"请求者 vs 数据主人"。**资源归属的全部实现**——安全依赖"每行数据都带主人标记（creator_id）"。

**补充发现（改进点）**：这段校验与修改链路（:465-477）**逻辑完全一样、代码是两份拷贝**（仅取用户时机和注释不同）。面试被问"有什么改进想法"可答：归属校验在修改/删除/可见性/置顶多处重复，可抽公共方法，或做成注解+AOP（如 `@CheckNoteOwnership`），与 operationlog 审计切面同一思路。

**两层防线**：网关 = 接口级权限（登录/权限点）；这里 = 资源级权限（数据是不是你的）。

## 第 2 步：删 Redis 两个 key（:600-602，直连）

`note_detail:1834567890123456` + `published_note_list:10001`。列表缓存存的是摘要，笔记没了列表必须失效。

## 第 3 步：逻辑删（:605-611）—— 逐行解剖

```java
NoteDO noteDO = NoteDO.builder()              // ① Lombok 建造者，未 set 的字段全 null
        .id(noteId)                           // ② 仅供 WHERE 定位
        .status(NoteStatusEnum.DELETED.getCode()) // ③ 枚举取数字 2，不用魔法数字
        .updateTime(LocalDateTime.now())      // ④ 记录删除时间
        .build();                             // ⑤ 只有三字段有值
noteDOMapper.updateByPrimaryKeySelective(noteDO); // ⑥
```

第⑥行 MyBatis 动态 SQL 全过程：XML 模板（`NoteDOMapper.xml:163-210`）14 列各有 `<if test="字段 != null">` → 逐列求值，仅 status（:202-204）和 updateTime（:199-201）命中 → 拼出最终 SQL：

```sql
UPDATE t_note SET update_time = '2026-11-20 16:00:00', `status` = 2
WHERE id = 1834567890123456;
```

→ MySQL 主键定位 → **旧值抄进 undo log**（回滚底片）→ status 1→2 → 标记未提交 → 返回影响行数 1。

**对照记忆**：修改用全字段无条件版（8 列全刷，表单提交全字段）；删除用 Selective 版（只动两列，防止把没提交的列刷成 null）。

**为什么逻辑删不物理删**：笔记被点赞/收藏/评论/计数/ES 引用，物理删留悬空引用；留痕可恢复、对账可追溯。

## 第 4 步：发两个 MQ 消息（:614、:617）

- **延迟消息**（asyncSend）：`DelayDeletePublishedNoteListRedisCacheTopic`，负载 `"10001"`，1 秒后第二删；
- **广播消息**（**syncSend**）：`DeleteNoteLocalCacheTopic`，负载 noteId——清所有实例 Caffeine。用 sync 的理由：缓存失效失败必须当场抛异常 → 回滚 → 用户看到"删除失败"，不允许静默脏缓存。

## 第 5 步：发删除事件（:622-646）

`asyncSend("NoteOperateTopic:Delete", NoteOperateMqDTO{creatorId:10001, noteId, type:0})`——与发布同 Topic、靠 Tag 区分。

## 第 6 步：返回用户

`Response.success()` → "删除成功"。**同步段结束。**

## 异步段

- **⑦ 广播生效**：所有 note 实例（含本实例）清本机 Caffeine；
- **⑧ 延迟第二删**（1 秒后）：再删 `published_note_list:10001`；
- **⑨ 计数 -1**：`CountNotePublishConsumer` 按 Tag=Delete 走 -1 分支：幂等键 `"DELETE:1834567890123456"`（一篇笔记一生只删一次，键天然唯一）→ Redis `count:user:10001` 的 note_total -1（key 存在才更）→ `t_user_count` 同步 -1（count 服务里的 MyBatis：`userCountDOMapper.insertOrUpdateNoteTotalByUserId`）；
- **⑩ ES 同步**：binlog → Canal（伪装成 MySQL 从库）→ search 服务下线该文档；
- **⑪ data-align**：记待办，夜间 XXL-JOB 对账。

## 删除后各存储最终状态

- **t_note**：行还在，status=2，查询接口状态过滤后不可见；
- **Cassandra 正文**：**不删**——content_uuid 失联成"孤岛"，用空间换链路简单（可起离线任务扫孤儿，面试主动提）；
- **t_note_like / 收藏 / 评论 / t_note_count**：**都不动**，前台无入口，留痕供对账；
- **t_user_count**：note_total -1；
- **Redis/Caffeine**：相关缓存全清。

## 两个边界的精确界定

**MyBatis 的边界**：本链路只有两处——`selectByPrimaryKey` 和 `updateByPrimaryKeySelective`（下游计数还有 `userCountDOMapper`）。删缓存是 RedisTemplate、发消息是 RocketMQTemplate、取用户是 ThreadLocal、清 Caffeine 是本地内存。**规律：见 `xxxDOMapper` 才是 MyBatis（去 MySQL），其余各有各的客户端。**

**@Transactional 的包裹范围**：形式上**整个方法体**都在代理的事务壳里（校验、删缓存、UPDATE、发消息全在壳内执行）；实质上**回滚保护只覆盖走当前连接的 MySQL 写**——本链路只有 status 翻转。Redis 删除执行即生效不可回滚（但幂等无害）；MQ 发出追不回（syncSend 失败会抛异常**触发**回滚，但已发出的消息本身撤不回）。面试口径："Redis 操作在事务的执行范围内，但不在事务的回滚范围内。"

## 失败全景

1. UPDATE 之前断 → 全部旧状态 → ✅
2. UPDATE 后中断/宕机 → MySQL 未提交自动作废（undo log）→ status 还是 1 → ✅
3. commit 后断 → 逻辑删生效；异步消息有 MQ 持久化+重试；缓存全丢还有 TTL → ✅

**删除链路没有跨存储窗口**：唯一的写是单库翻状态，Cassandra 不动，本地事务全覆盖——这是它比修改链路简单的根本原因。

## 面试官介绍稿（30 秒）

> 删除采用逻辑删：归属校验通过后，用 MyBatis Selective 更新把 t_note 的 status 翻成已删除，行保留。缓存和修改同款组合拳——直删 Redis、延迟补删、广播清本地缓存。然后发删除事件，计数服务按 Tag 给作者发文数减一，幂等键用"DELETE+笔记ID"，一篇笔记一生只删一次。正文不做级联删除，元数据不可见后自然失联，用空间换链路简单。搜索靠 Canal 监听 binlog 自动下线文档。

## 深挖追问清单

1. 为什么逻辑删？→ 引用遍布，物理删留悬空引用；留痕可恢复可追溯
2. 为什么用 Selective 而不是全字段更新？→ 防止把没提交的列刷成 null
3. 删笔记后点赞数变吗？→ 关系表和 t_note_count 不动，入口消失；计数保留、展示过滤

5. 广播失败？→ syncSend 当场抛异常 → 回滚 → status 翻回 → 用户看到失败
6. Redis 操作在事务里吗？→ 在执行范围内，不在回滚范围内
7. 校验代码和修改一样吗？→ 逻辑相同、两份拷贝；改进：抽公共方法或注解+AOP
