# 删除笔记 · 全链路事无巨细版

> 整理日期：2026-11-20
> 示例：**张三（userId=10001）删除自己的笔记（id=1834567890123456）。**
> 代码：`NoteServiceImpl.deleteNote`（:581-649，带 `@Transactional`）
> ⚠️ 重要勘误：逻辑删的 status 值是 **2**（枚举 `NoteStatusEnum`：NORMAL(1)=正常、DELETED(2)=已删除、DOWNED(3)=下架）。
> 建表脚本中"0-正常 1-删除"的注释是过时的错误注释，一切以代码为准。

## 第 0 步：前端发请求

```
POST http://47.100.x.x:8000/note/note/delete
Authorization: Bearer f4a9c2e1...（张三的 Token）

{ "id": 1834567890123456 }        // DeleteNoteReqVO 只有一个字段
```

入口段与发布/修改完全一致（验票 → userId 透传 → 路由 `/note/**` → 剥前缀 → Nacos → 负载均衡 → 身份入柜 → Spring 分发到 `deleteNote()`），详见《发布笔记链路全解剖》第 1~4 步。

## 第 1 步：存在性 + 归属校验（:586-597）

```java
NoteDO selectNoteDO = noteDOMapper.selectByPrimaryKey(noteId);          // ① 查
if (Objects.isNull(selectNoteDO)) {
    throw new BizException(ResponseCodeEnum.NOTE_NOT_FOUND);            // ② 不存在就抛
}
Long currUserId = LoginUserContextHolder.getUserId();                   // ③ 取当前用户
if (!Objects.equals(currUserId, selectNoteDO.getCreatorId())) {
    throw new BizException(ResponseCodeEnum.NOTE_CANT_OPERATE);         // ④ 不是本人就抛
}
```

**第①行背后（MyBatis 全流程）**：
1. `noteDOMapper` 是 MyBatis Mapper 接口，启动时 MyBatis 生成代理对象；
2. 按方法名找到 XML 里的 SQL：`SELECT id, title, creator_id, status, ... FROM t_note WHERE id = #{id}`；
3. noteId 填入 `#{id}`（预编译占位符，防 SQL 注入）；
4. MySQL 用主键索引直接定位（主键查询最快，不扫表）；
5. 结果集每列映射成 NoteDO 字段（`creator_id` 列 → `creatorId` 属性），返回对象。

**第②行**：`throw` 后方法立即中断，异常被全局异常处理器转成统一错误响应（`{"code":"NOTE_NOT_FOUND",...}`）。方法带 `@Transactional`，抛异常同时触发回滚（此处还没改数据，回滚无实际影响）。

**第③行**：从当前线程的 ThreadLocal 取出入口过滤器存好的 10001，无参数、无查询。

**第④行**：纯内存比较。"资源归属"的全部实现 = 拿"请求者"和"数据主人（creator_id）"对比——安全不依赖花哨机制，依赖"每一行数据都带着主人标记"。

两层防线概念：网关 = 接口级权限（登录了吗、接口要不要权限点）；这里 = 资源级权限（这条数据是不是你的）。

## 第 2 步：删 Redis 两个 key（:600-602，直连不走 MQ）

- `note_detail:1834567890123456`（详情缓存）
- `published_note_list:10001`（张三主页列表缓存——列表里还展示着这篇摘要，必须失效）

## 第 3 步：逻辑删（:605-611，事务内）—— 逐行解剖

```java
NoteDO noteDO = NoteDO.builder()                                    // 第1行
        .id(noteId)                                                 // 第2行
        .status(NoteStatusEnum.DELETED.getCode())                   // 第3行
        .updateTime(LocalDateTime.now())                            // 第4行
        .build();                                                   // 第5行
noteDOMapper.updateByPrimaryKeySelective(noteDO);                   // 第6行
```

- **第 1 行**：Lombok `@Builder` 生成空建造者——后面 set 什么才有什么，没 set 的字段全是 **null**（这是"只更新两列"的前提）。
- **第 2 行**：`.id(1834567890123456)`，不进 SET 列，给最后 `WHERE id = ?` 定位用。
- **第 3 行**：`DELETED.getCode()` 取出数字 **2**。枚举的意义：给魔法数字起名，改编码只动枚举一处。
- **第 4 行**：记录删除时间。
- **第 5 行**：组装完成——这个 NoteDO 只有三个字段有值，其余全 null。
- **第 6 行 MyBatis 动态 SQL 全过程**：
  1. 打开 XML 模板（`NoteDOMapper.xml:163-210`），`<set>` 里 14 列每列都有 `<if test="字段 != null">`；
  2. 逐列求值：title？null → 跳过…… status？=2 **命中**（:202-204），updateTime？有值 **命中**（:199-201），其余 12 列全跳过；
  3. 拼出最终 SQL：
     ```sql
     UPDATE t_note SET update_time = '2026-11-20 16:00:00', `status` = 2
     WHERE id = 1834567890123456;
     ```
  4. MySQL 执行：主键定位 → **旧值抄进 undo log**（回滚底片）→ status 从 1 改成 2 → 标记未提交（commit 由 @Transactional 在方法成功结束时发出）；
  5. 返回影响行数 1。

**与修改链路的对照**：修改用"全字段无条件"版 `updateByPrimaryKey`（8 列写死全刷，编辑表单提交全部字段）；删除用 Selective 版（动态只更新非空列）——删除请求不提交内容字段，若用全字段版会把标题等内容全刷成 null。

**为什么逻辑删不物理删**（必背）：笔记被点赞、收藏、评论、计数、ES 索引到处引用，物理删留下一片悬空引用；逻辑删留痕，运营/审核可恢复，对账链路可追溯。

## 第 4 步：发两个 MQ 消息（:614、:617）

- **延迟消息**（asyncSend）：`DelayDeletePublishedNoteListRedisCacheTopic`，负载 `"10001"`，延迟级别 1（1 秒）——延迟双删的第二删；
- **广播消息**（**syncSend**）：`DeleteNoteLocalCacheTopic`，负载 `"1834567890123456"`——清所有实例 Caffeine。同步发送的理由：缓存失效失败必须当场抛异常 → 回滚 → 用户看到"删除失败"，不允许"用户看到成功但缓存静默没清"。

## 第 5 步：发删除事件（:622-646）

`asyncSend("NoteOperateTopic:Delete", NoteOperateMqDTO{creatorId:10001, noteId:1834567890123456, type:0})`——与发布事件**同一个 Topic，靠 Tag 区分**（Publish / Delete）。

## 第 6 步：返回用户

`Response.success()` → 前端显示"删除成功"。**同步段结束。**

## 异步段

**⑦ 广播生效**：所有 note 实例清掉本机 Caffeine 里这篇笔记（含处理本请求的实例自己）。

**⑧ 延迟第二删**：1 秒后再删 `published_note_list:10001`。

**⑨ 计数 -1**：`CountNotePublishConsumer` 收到消息，Tag=Delete 走 -1 分支（消费者 :61-62）：
- **幂等前置**：键为 `"DELETE:1834567890123456"`——同一篇笔记一生只删除一次，业务键天然唯一；
- Redis `count:user:10001` 的 `note_total` -1（key 存在才更）；`t_user_count` 同步 -1。

**⑩ ES 同步**：status 变化写入 binlog → Canal（伪装成 MySQL 从库）捕获 → search 服务重建/下线该文档，搜索结果里这篇消失。

**⑪ data-align**：对账消费者记下变更，夜间 XXL-JOB 校正发布数。

## 删除之后，各存储的最终状态

- **t_note**：行还在，`status=2`。查询接口带状态过滤，用户不可见。
- **Cassandra 正文**：**不删**。content_uuid 随元数据不可见而失联，成为"访问不到的孤岛"。为什么不做级联删除：跨存储级联删又是一次双写一致性问题，用少量空间换链路简单；真要清理可起离线任务扫孤儿（面试主动提的改进点）。
- **t_note_like / t_note_collection / 评论 / t_note_count**：**都不动**。前台无展示入口；真相表留痕供对账追溯。
- **t_user_count**：作者行 `note_total -1`。
- **Redis / Caffeine**：相关缓存全清。

## 失败全景（@Transactional 保护范围：校验后 → 删缓存 → UPDATE → 发消息）

1. UPDATE 之前断 → 全部旧状态 → ✅
2. UPDATE 后中断/宕机 → MySQL 未提交自动作废（undo log）→ status 还是 1 → ✅
3. commit 后断 → 逻辑删已生效；异步消息靠 MQ 持久化+重试兜底；缓存第一次已直删、第二次有延迟消息，全丢还有 TTL 兜底 → ✅

**删除链路没有跨存储不一致窗口**：唯一的写就是 MySQL 翻状态，单库操作被本地事务完全覆盖，Cassandra 不动。这是它比修改链路简单的根本原因。

## 面试官介绍稿（30 秒）

> 删除采用逻辑删：归属校验通过后，用 MyBatis Selective 更新把 t_note 的 status 翻成已删除，行保留。缓存处理和修改同款——直删 Redis、延迟补删、广播清本地缓存。然后发删除事件，计数服务按 Tag 给作者发文数减一，幂等键用"DELETE+笔记ID"，因为同一篇笔记一生只删一次。正文不做级联删除——元数据不可见后正文自然失联，用空间换链路简单。搜索侧靠 Canal 监听 binlog 自动下线文档。

1. 为什么逻辑删？→ 引用遍布点赞/评论/计数，物理删留悬空引用；留痕可恢复可追溯

3. 删笔记后点赞数会变吗？→ t_note_count 不动、关系表不动；只是入口消失。口径：计数保留，展示层过滤

5. 广播失败会怎样？→ syncSend 当场抛异常 → @Transactional 回滚 → status 翻回 → 用户看到失败
6. Cassandra 孤儿正文怎么办？→ 现状容忍；改进：离线任务定期扫描清理
7. 删除链路为什么没有跨存储窗口？→ 唯一写入是单库翻状态，本地事务全覆盖；Cassandra 不动
