# 幂等对照实验证据留存 —— 2026-10-14 下午

> 简历数字唯一出处。实验工具：`shiguang-benchmark/MqIdempotencyReplayBenchmark`
> 方法：向 `CountFansTopic` 重放同一业务消息 `{"userId":90001,"targetUserId":90002,"type":1}` 共 100 次，
> 观察 `t_user_count.fans_total`(user_id=90002) 变化。开关经 JVM 参数 `-Dmq.dedup.enabled` 控制。

## Round 1 —— 幂等开关 OFF（-Dmq.dedup.enabled=false，15:11 重启 count）

- 基线：`t_user_count` 无 90002 行
- 重放：100/100 发送成功，耗时 955ms
- count.log 15:13:38：聚合缓冲区收到 100 条相同消息 → 聚合结果 `{"90002":100}`
- CountFans2DBConsumer：`insertOrUpdateFansTotalByUserId Parameters: 90002, 100, 100`
- **结果：fans_total = 100（计数污染 +100，上游缺陷复现）**

## Round 2 —— 幂等开关 ON（默认 true，15:15 重启 count）

- 重放：同消息再发 100 次
- count.log 15:15:58：`DedupServiceImpl ==> [幂等] Redis 前置判重拦截重复消息, bizKey: CountFansTopic:90001:90002:FOLLOW`（99 条拦截，多消费线程并发记录）
- 15:15:59：聚合缓冲区仅 1 条 → 聚合结果 `{"90002":1}` → DB `Parameters: 90002, 1, 1`
- **结果：fans_total 100 → 101（仅 +1，修复验证通过）**
- Redis 证据：`mq:dedup:CountFansTopic:90001:90002:FOLLOW` 存在（SETNX 7d TTL）

## 结论（简历可用 L4 文案）

重放对照实验：同一关注业务消息重投 100 次——开关关闭（复现上游缺陷）粉丝计数 +100；
开关开启后仅首次生效，计数 +1，其余 99 次被 Redis SETNX 前置判重拦截（业务键 topic:userId:targetId:action，MySQL 唯一索引兜底）。
