# 幂等对照实验证据留存 —— 2026-10-14

> 简历数字唯一出处。实验工具：`shiguang-benchmark/MqIdempotencyReplayBenchmark`
> 方法：向 `CountFansTopic` 重放同一业务事件消息 100 次，
> 观察 `t_user_count.fans_total`(user_id=90002) 变化。开关经 JVM 参数 `-Dmq.dedup.enabled` 控制。

## v2 实验（幂等键=业务事件 ID 版本，16:08-16:12）

消息体：`{"userId":90001,"targetUserId":90002,"type":1,"eventId":"benchmark-replay-90001-90002"}`
（固定 eventId = 模拟同一业务事件的 100 次重复投递）

- **Round OFF**（`-Dmq.dedup.enabled=false` 重启 count）：聚合 `{"90002":100}` → **fans_total = +100**（缺陷复现）
- **Round ON**（默认开启）：99 条被 SETNX 判重拦截（键 `mq:dedup:CountFansTopic:benchmark-replay-90001-90002`），仅 1 条入聚合 → **fans_total 100 → 101（+1）**

## 回归验证：合法重复操作不被误拦（eventId 修复的直接证据）

场景：用户 101 关注 10001 → 取关 → **再次关注**（TTL 窗口内的合法重复动作）。

- 旧版幂等键为 `topic:userId:targetId:action`（7 天 TTL）：再关注的计数消息会被残留键
  `mq:dedup:CountFansTopic:101:10001:FOLLOW` 误拦 → fans_total 漏 +1
- 新版键为 `topic:eventId`：再关注生成新 eventId → 正常计数
- 实测（16:04-16:06）：取关后 fans_total(10001)=0；再关注后 fans_total(10001)=1 ✅，
  同时 Redis 中残留的旧格式键 `...:101:10001:FOLLOW` 仍然存在（对照）但不再影响新链路

## v1 实验（业务键=userId:targetId:action 版本，15:11-15:16，已被 v2 取代）

- OFF：100 条全入聚合 `{"90002":100}` → DB +100
- ON：99 条拦截（键 `mq:dedup:CountFansTopic:90001:90002:FOLLOW`）→ DB 100→101
- v1 暴露出"取关后再关注被误拦"缺陷 → 触发幂等键引入业务事件 ID 的修复（本文件 v2）

## 结论（简历 L4 文案数字出处）

重放对照实验：同一关注业务事件重投 100 次——开关关闭（复现上游缺陷）粉丝计数 +100；
开启后仅首次生效计数 +1，其余 99 次被 Redis SETNX 前置判重拦截
（幂等键=业务事件 ID，随消息体流转；MySQL 唯一索引兜底）；且取关后再关注等合法重复动作不受影响。
