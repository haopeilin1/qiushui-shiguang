# 笔记写路径全解：发布 / 修改 / 删除（字段级）

> 记录日期：2026-11-20
> 覆盖代码：`NoteServiceImpl.publishNote/updateNote/deleteNote`、`PublishNote2DBLocalTransactionListener`、
> `SaveNoteContentConsumer`、`DelayDeleteNoteRedisCacheConsumer`、`DelayDeletePublishedNoteListRedisCacheConsumer`、
> `DeleteNoteLocalCacheConsumer`、`CountNotePublishConsumer`、`CanalSchedule`
> 写法：每一步都说明"调了谁 / 生成什么 / 写哪张表哪几列 / 发什么 MQ"。

---

## 0. 先看总账：三个动作分别动了什么

| 动作 | `t_note` | Cassandra `note_content` | Redis | MQ |
|---|---|---|---|---|
| 发布（有正文） | INSERT 1 行（15 列） | 消费者 INSERT 1 行 | 删 `note:published:list:{creatorId}` | 事务消息 `PublishNoteTransactionTopic` → `NoteOperateTopic:publishNote` |
| 发布（无正文） | INSERT 1 行（15 列，content_uuid=null） | 不动 | 删列表缓存 + 延迟 1s 再删 | 直接 `NoteOperateTopic:publishNote` |
| 修改 | UPDATE 8 列 | 有正文 upsert / 清空 delete | 删详情 + 列表；广播清本地；延迟 1s 再删 | 不直接发（搜索靠 Canal） |
| 删除 | UPDATE 2 列（status=2） | **不动**（正文保留） | 删详情 + 列表；广播清本地 | `NoteOperateTopic:deleteNote` |

## 1. 发布笔记

### 1.1 入口参数（PublishNoteReqVO）

`title`、`type`（0 图文 / 1 视频）、`imgUris`（List）、`videoUri`、`content`、`topicId`

### 1.2 同步段：接口线程里做的事

**Step 1 校验类型**
`NoteTypeEnum.valueOf(type)`，不是 0/1 → `NOTE_TYPE_ERROR`。

**Step 2 按类型校验媒体**
- 图文：`imgUris` 非空且 ≤ 8 张，然后 `StringUtils.join(imgUriList, ",")` 拼成一个字符串；
- 视频：`videoUri` 非空。

**Step 3 生成 noteId（Feign 调 ID 服务）**
`distributedIdGeneratorRpcService.getNoteId()`（雪花 / Leaf 号段）。

**Step 4 决定正文与 contentUuid**
- `content` 非空 → `isContentEmpty=false`，`contentUuid = UUID.randomUUID().toString()`；
- `content` 为空 → `isContentEmpty=true`，`contentUuid=null`；
- 注意：真正的正文**不在这里写 Cassandra**，`keyValueRpcService.saveNoteContent` 那段已被注释掉（第 161-167 行）。

**Step 5 查话题名**
`topicId` 非空 → `topicDOMapper.selectNameByPrimaryKey(topicId)` 拿 `topicName`（冗余存一份）。

**Step 6 组装 NoteDO（这就是要写入 t_note 的东西）**

| t_note 列 | 值 |
|---|---|
| `id` | noteId（雪花） |
| `title` | req.title |
| `is_content_empty` | 正文空 = 1 / 非空 = 0 |
| `creator_id` | `LoginUserContextHolder.getUserId()` |
| `topic_id` | req.topicId（可 null） |
| `topic_name` | 由 topicId 查出（可 null） |
| `is_top` | `false` |
| `type` | req.type |
| `img_uris` | 逗号拼接后的字符串 |
| `video_uri` | req.videoUri |
| `visible` | `PUBLIC=0` |
| `create_time` / `update_time` | `now()` |
| `status` | `NORMAL=1` |
| `content_uuid` | 有正文 = UUID；无正文 = null |

**Step 7 分两条路**

**A. 正文为空 → 直接本地写库（不走事务消息）**

`processPublishContentEmptyNote`：

1. `DEL note:published:list:{creatorId}`（个人主页列表缓存）；
2. `INSERT INTO t_note (...15 列...)`；
3. 发延迟 1s 消息 `DelayDeletePublishedNoteListRedisCacheTopic`（延迟双删的第二次）；
4. 发 `NoteOperateTopic:publishNote`，消息体：
   ```json
   {"creatorId":10001,"noteId":123456,"type":1}
   ```
5. 返回成功。

**B. 有正文 → 事务消息（两阶段）**

1. `PublishNoteDTO` = NoteDO 的 15 个字段 + `content`（正文）。
2. `sendMessageInTransaction("PublishNoteTransactionTopic", message, null)` —— 先发**半消息**（对消费者不可见）。
3. Broker 回调 `executeLocalTransaction`（`PublishNote2DBLocalTransactionListener`）：
   - `DEL note:published:list:{creatorId}`；
   - `INSERT INTO t_note`；
   - 成功 → 发延迟删列表消息 + 发 `NoteOperateTopic:publishNote` → 返回 `COMMIT`；
   - 失败 → `ROLLBACK`（半消息丢弃，KV 永远收不到，正文也不会落库）。
4. 若生产者宕机没回话，Broker 回查 `checkLocalTransaction`：
   `SELECT count(1) FROM t_note WHERE id=? AND status=1` → 1 则 COMMIT，否则 ROLLBACK。

### 1.3 异步段：消息转正之后

**① KV 服务落正文**（`SaveNoteContentConsumer`）

- 消费 `PublishNoteTransactionTopic`；
- 取 `content`、`contentUuid`；
- `noteContentRepository.save(NoteContentDO(id=UUID.fromString(uuid), content=content))`；
- Cassandra 表 `note_content` **只有两列**：`id UUID 主键`、`content text`；
- `save` 是 upsert：同一个 uuid 再写一次就是覆盖。

**② 计数服务 +1**（`CountNotePublishConsumer`）

- 消费 `NoteOperateTopic`，tag=`publishNote`；
- 幂等键：`NoteOperateTopic:PUBLISH:{noteId}`；
- Redis：`HINCRBY count:user:{creatorId} noteTotal 1`（仅当 Hash 存在）；
- MySQL：
  ```sql
  INSERT INTO t_user_count (user_id, note_total) VALUES (?, 1)
    ON DUPLICATE KEY UPDATE note_total = note_total + 1;
  ```

**③ 数据对齐记录**（`TodayNotePublishIncrementData2DBConsumer`）

- 布隆判重"今天是否已记录该 creatorId"；
- 没记过 → 插入 `t_data_align_note_publish_count_temp_{yyyyMMdd}_{creatorId % 3}`，**只存 user_id**；
- 供凌晨 XXL-JOB 用 `count(*)` 校准 `t_user_count.note_total`。

**④ 搜索索引**（Canal，不是 MQ）

- Canal 订阅 `t_note` 的 binlog；
- `INSERT` → `syncNoteIndex(noteId)`：聚合笔记 + 作者 + 计数，写 ES `note` 索引。

## 2. 修改笔记

### 2.1 同步段（方法上有 `@Transactional`）

**Step 1 校验类型 + 媒体**：与发布完全相同（图文 ≤ 8 张、视频非空）。

**Step 2 查笔记**
`noteDOMapper.selectByPrimaryKey(noteId)`（SQL 带 `status = 1`）→ 查不到抛 `NOTE_NOT_FOUND`。

**Step 3 权限**
`currUserId == selectNoteDO.creatorId`，否则 `NOTE_CANT_OPERATE`。

**Step 4 话题**
`topicId` 非空 → 查 `t_topic.name`；查不到抛 `TOPIC_NOT_FOUND`。

**Step 5 删 Redis（两个 key 一次 DEL）**
- `note:detail:{noteId}`
- `note:published:list:{currUserId}`

**Step 6 更新 `t_note`（只改 8 列）**

`noteDOMapper.updateByPrimaryKey(noteDO)`：

```sql
UPDATE t_note SET
  title = ?, is_content_empty = ?, topic_id = ?, topic_name = ?,
  `type` = ?, img_uris = ?, video_uri = ?, update_time = ?
WHERE id = ?;
```

**注意：这条 SQL 不动 `creator_id` / `visible` / `status` / `is_top` / `content_uuid`。**

**Step 7 延迟双删（第二次）**
发延迟 1s 消息 `DelayDeleteNoteRedisCacheTopic`，消息体 `[noteId, currUserId]`。

**Step 8 广播清本地缓存**
`syncSend("DeleteNoteLocalCacheTopic", noteId)` → 所有 note 实例执行 `LOCAL_CACHE.invalidate(noteId)`。

**Step 9 正文处理（先查旧 contentUuid）**

| 情况 | 动作 |
|---|---|
| 新 content 为空 | `keyValueRpcService.deleteNoteContent(contentUuid)` → Cassandra `deleteById(uuid)` |
| 新 content 非空、旧 uuid 存在 | `saveNoteContent(旧uuid, content)` → Cassandra upsert（覆盖正文） |
| 新 content 非空、旧 uuid 为空 | 生成新 UUID → `saveNoteContent(新uuid, content)` |

失败 → 抛 `NOTE_UPDATE_FAIL` → 本地事务回滚。

### 2.2 异步段

- 延迟消费者：1 秒后删 `note:detail:{noteId}` 和"已发布列表"缓存；
- 搜索（Canal 监听 `t_note` 的 UPDATE）：
  - `status=1 且 visible=0` → `syncNoteIndex(noteId)`（覆盖更新 ES 文档）；
  - `visible=1` 或 `status=2/3` → `deleteNoteDocument(noteId)`（从 ES 删掉）。

### 2.3 另外两个"改"操作（顺带补齐）

| 操作 | UPDATE 列 | 缓存动作 |
|---|---|---|
| `visibleOnlyMe` | `visible=1`、`update_time`（`where status=1`） | 删详情缓存 + 广播清本地 |
| `topNote` | `is_top`、`update_time`（`where creator_id=当前用户`） | 删详情缓存 + 广播清本地 |

## 3. 删除笔记

### 3.1 同步段（`@Transactional`）

**Step 1 查笔记**：`selectByPrimaryKey`（status=1），不存在 → `NOTE_NOT_FOUND`。

**Step 2 权限**：非作者 → `NOTE_CANT_OPERATE`。

**Step 3 删 Redis**：`note:detail:{noteId}` + `note:published:list:{currUserId}`。

**Step 4 逻辑删除（只改 2 列）**

```sql
UPDATE t_note SET `status` = 2, update_time = ?
WHERE id = ?;
```

（走 `updateByPrimaryKeySelective`，只把非 null 的 `status`、`update_time` 拼进 SET。）

**Step 5 延迟双删**：发延迟 1s 的"删已发布列表"消息。

**Step 6 广播清本地缓存**：`DeleteNoteLocalCacheTopic`。

**Step 7 发 `NoteOperateTopic:deleteNote`**：

```json
{"creatorId":10001,"noteId":123456,"type":0}
```

### 3.2 异步段

| 谁 | 做什么 |
|---|---|
| `CountNotePublishConsumer` | tag=deleteNote → `HINCRBY count:user:{creatorId} noteTotal -1`；`t_user_count.note_total - 1`（幂等键 `NoteOperateTopic:DELETE:{noteId}`） |
| `TodayNotePublishIncrementData2DBConsumer` | 记录 creatorId 到发布数临时表，凌晨对账 |
| Canal | `UPDATE t_note SET status=2` → `deleteNoteDocument(noteId)`，ES 删除文档 |

### 3.3 删除"没有删"什么（面试常问）

- **Cassandra 正文不删**：`note_content` 那一行还在（留档 / 可恢复）；
- **评论不删**：`t_comment` 里挂在该 note 下的评论仍在；
- **点赞/收藏关系不删**：`t_note_like` / `t_note_collection` 原样保留；
- **计数行不删**：`t_note_count` 那一行还在（只是详情页已经查不到这篇笔记）。

所以"删除笔记"准确说是 **`t_note.status=2` 的软删除 + 缓存失效 + ES 下架 + 作者发布数 -1**，
不是数据库级联清理。要彻底清理，需要额外写清理任务（当前没有）。

## 4. 字段级总账（复习只看这一节）

### 4.1 写表总账

| 表 | 操作 | 涉及列 |
|---|---|---|
| `t_note` | INSERT（发布） | id, title, is_content_empty, creator_id, topic_id, topic_name, is_top, type, img_uris, video_uri, visible, create_time, update_time, status, content_uuid（15 列） |
| `t_note` | UPDATE（修改） | title, is_content_empty, topic_id, topic_name, type, img_uris, video_uri, update_time（8 列） |
| `t_note` | UPDATE（删除） | status=2, update_time（2 列） |
| `t_note` | UPDATE（可见性） | visible=1, update_time |
| `t_note` | UPDATE（置顶） | is_top, update_time |
| `note_content`（Cassandra） | INSERT / UPSERT | id(UUID 主键), content |
| `note_content`（Cassandra） | DELETE | id |
| `t_user_count` | INSERT ... ON DUPLICATE KEY | user_id, note_total（发布 +1 / 删除 -1） |

### 4.2 Redis / 本地缓存

| Key | 什么时候删 |
|---|---|
| `note:detail:{noteId}` | 修改、删除、可见性、置顶时立即删；修改时 1s 后再删一次 |
| `note:published:list:{userId}` | 发布（立即 + 延迟 1s）、修改（立即 + 延迟 1s）、删除（立即 + 延迟 1s） |
| Caffeine `LOCAL_CACHE` | 修改、删除、可见性、置顶时发广播 `DeleteNoteLocalCacheTopic`，所有实例清 |

### 4.3 三件事用到的 MQ

| Topic : Tag | 谁发 | 谁收 | 作用 |
|---|---|---|---|
| `PublishNoteTransactionTopic`（事务消息） | `publishNote` | kv `SaveNoteContentConsumer`；Broker 回查 note 服务 | 正文落 Cassandra，和 t_note 插入对齐 |
| `NoteOperateTopic:publishNote` | 发布路径（含事务监听器） | count 发布数 +1、data-align 记录 | 计数 / 对账 |
| `NoteOperateTopic:deleteNote` | `deleteNote` | count 发布数 -1、data-align 记录 | 计数 / 对账 |
| `DelayDeletePublishedNoteListRedisCacheTopic` | 发布 / 删除 | 延迟消费者 | 1s 后删主页列表缓存 |
| `DelayDeleteNoteRedisCacheTopic` | 修改 | 延迟消费者 | 1s 后删详情 + 列表缓存 |
| `DeleteNoteLocalCacheTopic`（BROADCASTING） | 修改 / 删除 / 可见性 / 置顶 | 所有 note 实例 | 清 Caffeine |

## 5. 代码里的坑（面试前必须知道）

### 坑 1：空正文笔记改成有正文，`content_uuid` 没写回 t_note（已于 2026-11-20 修复）

`updateNote` 的 `updateByPrimaryKey` **不包含 `content_uuid` 列**，但后面的逻辑在旧 uuid 为空时会：
生成新 UUID → 正文写进 Cassandra。结果：

- `t_note.is_content_empty = 0`（详情页会去取正文）；
- `t_note.content_uuid` 仍然是 `NULL`；
- 详情页 `keyValueRpcService.findNoteContent(null)` → KV 侧 `UUID.fromString(null)` 抛异常。

**修复**：新增 `NoteDOMapper.updateContentUuid(id, uuid)`；
先写 KV，成功后再回写 `t_note.content_uuid`，保证 DB 不会指向 Cassandra 里不存在的 UUID。

### 坑 2：清空正文时，`content_uuid` 没置空（已于 2026-11-20 修复）

原实现 `deleteNoteContent` 删了 Cassandra 的行，但 `t_note.content_uuid` 仍指向已删除的 UUID。
现在删除成功后调用 `updateContentUuid(noteId, null)` 置空。

### 坑 3：延迟删除消费者拼错了 key（已于 2026-11-20 修复）

`DelayDeleteNoteRedisCacheConsumer` 收到的消息是 `[noteId, userId]`，但拼"已发布列表"缓存时用了：

```java
String publishedNoteListRedisKey = RedisKeyConstants.buildPublishedNoteListKey(noteId); // ← 应为 userId
```

结果第二次删除删的是 `note:published:list:{noteId}`（不存在的 key）。
**修复**：改为 `buildPublishedNoteListKey(userId)`。

### 坑 4：无正文发布分支，insert 和 MQ 不是原子的

`processPublishContentEmptyNote` 里：

```
DEL 列表缓存 → INSERT t_note → 发延迟消息 → 发 NoteOperateTopic
```

方法上没有事务，MQ 也是 asyncSend（失败只打日志）。若 INSERT 成功、MQ 发送失败：
`t_user_count.note_total` 少 1，且 data-align 也没记录 → **不会自愈**（直到该用户下次发布）。

有正文的分支因为有事务消息 + 回查，这个问题被堵住了。

### 坑 5：事务监听器里的"本地事务"是单条 insert（autocommit）

`executeLocalTransaction` 没有 `@Transactional`，`noteDOMapper.insert` 自身提交。
半消息机制保证"消息可见性 ↔ 笔记是否存在"，但其中的 `NoteOperateTopic` 发送仍是 fire-and-forget。

### 坑 6：删除是"半套清理"

`status=2` 之后，Cassandra 正文、评论、点赞/收藏关系、`t_note_count` 全部保留。
好处是留档可恢复；坏处是数据会一直占空间，需要额外的归档/清理任务（当前没有）。

### 坑 7：`t_note.status` 的 schema 注释与代码相反（已于 2026-11-20 修复）

- 代码：`BE_EXAMINE=0`、`NORMAL=1`、`DELETED=2`、`DOWNED=3`；
- 原 `sql/01_schema.sql` 注释写的是 `0-正常 1-删除`；
- 所有查询都按 `status=1` 取正常笔记，删除写 2。

注释已改为"0-待审核 1-正常 2-删除 3-下架"。

### 坑 8：修改不直接通知搜索，完全依赖 Canal

`updateNote` 不发 `NoteOperateTopic`；ES 更新靠 Canal 监听 `t_note` 的 binlog。
如果本地没启动 Canal（很常见），会出现"笔记改了、搜索里还是旧的"。

## 6. 面试口径（30 秒）

> "发笔记分两条路：
> 正文为空时直接 `INSERT t_note` 然后发 `NoteOperateTopic` 做计数；
> 正文不为空时用 RocketMQ **事务消息**：先发半消息，Broker 回调我执行本地事务（insert t_note），
> 成功才 COMMIT，kv 服务收到正式消息后把正文写 Cassandra；生产者宕机就靠回查 `select t_note` 裁决。
> 改笔记是 `UPDATE` 8 列 + 删详情/列表缓存 + 广播清本地 + 延迟双删，正文走 KV 覆盖或删除。
> 删笔记是软删 `status=2` + 缓存失效 + ES 下架 + 作者发布数 -1，正文和互动数据都保留。
> 搜索同步走 Canal 监听 binlog，不走业务 MQ。"
