# 修改笔记 · 全链路事无巨细版

> 整理日期：2026-11-20
> 示例：**张三（userId=10001）修改自己的笔记（id=1834567890123456）——改标题、改正文、话题从 5 换成 7。**
> 代码：`NoteServiceImpl.updateNote`（:427-543，带 `@Transactional(rollbackFor = Exception.class)`）

---

## 第 0 步：前端发请求

```
POST http://47.100.x.x:8000/note/note/update
Authorization: Bearer f4a9c2e1...（张三的 Token）

{
  "id": 1834567890123456,          // 比发布请求多出的关键字段：改哪篇
  "type": 0,
  "title": "我们部门的代码评审经验（2026 修订版）",
  "content": "分享一下我们团队坚持了两年的评审流程，补充第三章……",
  "imgUris": ["aaa.jpg","bbb.jpg"],
  "topicId": 7
}
```

入口段与发布完全一致（验票 → userId 透传 → 路由 → Nacos → 负载均衡 → 过滤器身份入柜 → Spring 分发），唯一差别：路径 `/note/note/update` 剥前缀后命中 `@PostMapping("/update")`。详见《发布笔记链路全解剖》第 1~4 步。

## 第 1 步：校验三连（:435-487）

1. **类型/图片校验**：type=0 图文 ✓，2 张图 ≤8 ✓，拼成 `"aaa.jpg,bbb.jpg"`；
2. **笔记存在性**：`SELECT * FROM t_note WHERE id=1834567890123456` → 查到旧行（creator_id=10001），查不到抛 `NOTE_NOT_FOUND`；
3. **归属校验**（发布没有、修改/删除都有的一道闸）：ThreadLocal 里的 10001 == 该行的 creator_id 10001 ✓ 放行；李四来改，≠ 抛 `NOTE_CANT_OPERATE`。

**两层防线**（必背）：网关 = 接口级权限（登录了吗、接口要不要权限点）；这里 = 资源级权限（这条数据是不是你的）——只有业务层拿着数据才能判。

## 第 2 步：删 Redis 两个 key（:490-492，直连不走 MQ）

- `note_detail:1834567890123456`（详情缓存）
- `published_note_list:10001`（张三主页列表缓存）

**为什么改笔记还要删列表缓存**：列表缓存里存的是**笔记摘要**（标题、封面、时间），主页列表直接展示。标题/封面变了，不删则别人看到旧标题旧封面。原则：**笔记的展示信息变了，所有展示它的地方的缓存都要失效。**

## 第 3 步：UPDATE t_note（:496-508，事务内）

`noteDOMapper.updateByPrimaryKey(noteDO)` → 真实 SQL（`NoteDOMapper.xml:211-222`）：

```sql
UPDATE t_note SET title='我们部门的代码评审经验（2026 修订版）',
                  is_content_empty=0, topic_id=7, topic_name='技术分享',
                  type=0, img_uris='aaa.jpg,bbb.jpg', video_uri=null,
                  update_time='2026-11-20 15:30:00'
WHERE id=1834567890123456;
```

**"全字段无条件更新"**：8 列写死在 SET 里，没有 `<if>` 判断，每次全更新。对比删除用的 `updateByPrimaryKeySelective`：MyBatis 动态 SQL `<if test="字段 != null">`，null 字段不进 SET（删除只刷 status 一列）。取舍：Selective 安全但 SQL 动态生成；全字段版简单粗暴，适合"编辑表单本来就提交全部字段"。
**不动的字段**：id、creator_id、status、visible、create_time；content_uuid 本例不变（原有正文，复用旧钥匙）。

## 第 4 步：@Transactional 到底包了什么（本链路最重要的机制）

注解自身不执行逻辑，是贴给 Spring 的标签。Spring 用**代理对象**在方法外包一层壳，等价于：

```java
connection.setAutoCommit(false);   // 开启事务：之后 SQL 都是"预改"
try {
    updateNote(...)                // 方法体：UPDATE、发消息、调 kv
    connection.commit();           // 正常走完 → 提交，修改真正生效
} catch (Exception e) {
    connection.rollback();         // 抛异常 → 回滚，预改全部作废
}
```

四个必须记住的点：

1. **"先 UPDATE 后调 kv"不等于"元数据先生效"**：UPDATE 执行时只是"预改"（未提交，对别人不可见），commit 发生在方法最后——**比 kv 写入还晚**。这是一切一致性分析的基石。
2. **回滚靠 undo log**：MySQL 改数据前自动把旧值抄一份，回滚 = 拿抄件还原。进程宕机时连接断开，未提交事务由 MySQL 自动作废，无需代码介入。
3. **`rollbackFor = Exception.class`**：Spring 默认只对运行时异常回滚，受检异常不回滚——加这个参数堵死默认规则的坑。
4. **自调用失效**：事务逻辑长在代理壳上，同类里 `this.updateNote()` 绕过代理，注解**不生效**。口诀：注解的功能在代理上，this 调用绕开代理。

## 第 5 步：发两个 MQ 消息（:512、:517）

- **5a 延迟消息**（asyncSend）：`DelayDeleteNoteRedisCacheTopic`，负载 `[1834567890123456, 10001]`，延迟级别 1（1 秒）——延迟双删的闹钟。
- **5b 广播消息**（**syncSend**）：`DeleteNoteLocalCacheTopic`，负载 `"1834567890123456"`——清所有实例 Caffeine。

**三种发送方式的两个维度**：
- 维度一"要不要等 MQ 回执"：syncSend（等，失败当场抛异常）vs asyncSend（不等，回调打日志）；
- 维度二"消息和数据库要不要原子绑定"：普通消息 vs 事务消息（半消息+回查）。

选型理由：
- 广播用 sync：缓存失效是正确性动作，**发送失败必须当场变异常 → 回滚 → 用户看到失败**，绝不允许"用户看到成功但缓存静默没清"；
- 广播**不需要**事务绑定：**删缓存幂等且方向安全**——多删无害（重建出来还是正确数据），漏删才有害（sync 已当场抓住）。对比发布的正文消息：消息发了但库回滚 → 孤儿正文（有害），所以必须事务绑定。**口诀：消息消费动作对回滚越有害，越需要事务消息。**
- 本实例自己的 Caffeine 也由这条广播删（广播发给所有实例含自己；:515 注释掉的 `LOCAL_CACHE.invalidate` 证明作者放弃"本机直删"、统一走广播）。

## 第 6 步：同步 Feign 调 kv（:522-540，事务最后一步）

三种情况：
- 改完还有正文 → `saveNoteContent(uuid, 新内容)`：Cassandra **覆盖写**；
- 把正文删空了 → `deleteNoteContent(uuid)`：**删除**正文；
- 原来没正文这次加了 → 先生成新 uuid 再 save：**新增**，新 uuid 记回 t_note。

**为什么修改敢同步、发布必须事务消息**（核心设计差异）：修改前存在干净的旧状态（旧元数据+旧正文互相匹配），kv 失败 → 抛异常 → 回滚 MySQL → 两边一起退回旧状态。发布是从无到有，**没有旧状态可退**，只能保证"存正文任务绝对不丢"→ 事务消息。**口诀：能回滚的用本地事务，没法回滚的用可靠消息。**（佐证：发布链路 :162-167 留着被注释的同步 Feign 代码——原作者最初也是同步，后来才改事务消息。）

## 第 7 步：失败全景（四种断点）

1. UPDATE 之前断 → 两边都旧 → ✅ 一致
2. UPDATE 后、kv 前断 → MySQL 未提交被作废，kv 没动 → ✅ 都旧
3. **kv 成功后、commit 前断 → MySQL 作废（元数据旧），Cassandra 已新 → ❌ 唯一不一致窗口，几毫秒**（kv 放最后一步把窗口压到物理最小；方向固定"元数据旧、正文新"）
4. commit 后断 → kv 早已成功，MySQL 已提交 → ✅ 都新

**诚实边界**：`@Transactional` 只能回滚 MySQL，Cassandra 写入不参与回滚；彻底消灭窗口需给修改也上事务消息，但有旧状态兜底、频率低，权衡后不值得。

## 第 8 步：返回用户

`Response.success()` → 前端显示"修改成功"。**同步段结束。**

## 异步段

**⑨ 广播生效（毫秒级）**：所有 note 实例的 `DeleteNoteLocalCacheConsumer`（已核实 `messageModel = BROADCASTING`）→ 各自 `LOCAL_CACHE.invalidate(noteId)`。（可见性、置顶、删除接口 :617/:695/:736 全复用这套。）

**⑩ 延迟双删第②删（1 秒后）**：`DelayDeleteNoteRedisCacheConsumer` 收到 `[noteId, userId]` → 再删详情缓存 + 列表缓存。
**⚠️ 我们发现并修复的真实 bug**（提交 `4bdfdb4`）：原代码 :44 拼列表 key 时误用 noteId（应为 userId），第二次删除永远删一个不存在的 key，延迟双删对列表缓存形同虚设。三条证据：key 构造函数 javadoc 写明 `@param userId`、发布链路传的确实是 creatorId、消费者取出了 userId 却未使用（取对变量、用错变量）。已一行修复。

**⑪ ES 索引同步（业务代码零参与）**：UPDATE 落库 → MySQL 自动记 binlog → Canal（伪装成 MySQL 从库）捕获变更 → search 服务 CanalClient 重建 ES 文档。
**ES 是什么**：专门做全文搜索的数据库。MySQL `LIKE '%关键词%'` 用不上索引全表扫、不会分词、不会相关度排序；ES 用**倒排索引**（文本拆词 → 建"词→文档列表"反向表），毫秒级命中、支持分词和相关度。定位：**MySQL 管"存得准"，ES 管"搜得到"**。
**为什么修改不用发 MQ 通知搜索**：binlog 覆盖一切变更（含直接改库），比显式发事件更全；代价是多维护 Canal 一套组件。

## 数据落点清单

- MySQL `t_note`：8 个内容字段更新 + update_time（同步，事务内）
- Cassandra `note_content`：覆盖写/删除（同步 Feign，事务最后一步）
- Redis：`note_detail:{noteId}` + `published_note_list:{userId}` 删除（立即 + 1 秒后第二次）
- Caffeine（所有 note 实例）：广播失效该笔记（毫秒级）
- ES：Canal 监听 binlog 自动重建文档（异步）
- **不动的**：t_user_count（修改不影响计数）、t_note_like 等关系表

## 面试官介绍稿（40 秒）

> 修改笔记的核心是三件事：权限、一致性、缓存。权限上除了网关的接口级校验，业务层还有资源归属校验——非作者直接拒绝。一致性上，元数据更新在 `@Transactional` 本地事务里，Cassandra 正文用同步 Feign 放在事务最后一步，它失败就回滚，两边要么一起新要么一起旧；和发布链路的事务消息是两种方案，因为修改有旧状态可以回滚，发布没有。缓存上是一套组合拳：先删 Redis 详情和列表缓存，延迟一秒补删，再发广播清所有实例的本地缓存。搜索索引不用业务代码管——Canal 监听 binlog 自动同步 ES。

## 深挖追问清单（含口径）

1. updateByPrimaryKey vs Selective？→ 前者 8 列写死全更新（修改），后者 `<if>` 动态只更新非空列（删除翻 status）
2. 广播消息丢了？→ Caffeine 1 小时 TTL 兜底，错误最多残留一个周期
3. 为什么广播用 syncSend？→ 缓存失效失败必须当场可感知、触发回滚；删缓存幂等无害所以不需要事务绑定
4. kv 超时？→ Feign 超时即失败 → 抛异常 → 回滚，用户重试
5. 延迟双删为什么 1 秒？→ 大于一次回源+回填耗时，RocketMQ 预定义延迟档
6. 唯一不一致窗口？→ kv 成功到 commit 之间几毫秒，方向"元数据旧正文新"，kv 放最后压到最小
7. 事务消息为什么不用在修改？→ 有旧状态可回滚，本地事务更简单；事务消息留给"无旧状态可退"的发布
8. 我们修的 bug？→ 延迟消费者 key 拼错（noteId 误作 userId），三证据确认，一行修复
