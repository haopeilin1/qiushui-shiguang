# 修改笔记 · 全链路事无巨细版

示例：张三（userId=10001）修改自己的笔记（id=1834567890123456）——改标题、改正文、话题从 5 换成 7。

## 第 0 步：前端发请求

```
POST http://47.100.x.x:8000/note/note/update
Authorization: Bearer f4a9c2e1...（张三的 Token）

{
  "id": 1834567890123456,          // 比发布请求多出的关键字段：改哪篇
  "type": 0,
  "title": "我们部门的代码评审经验（2026 修订版）",
  "content": "分享一下我们团队坚持了两年的评审流程，补充第三章……",
  "imgUris": ["aaa.jpg","bbb.jpg"],
  "topicId": 7
}
```

入口段与发布完全一致（验票 → userId 透传 → 路由 → Nacos → 负载均衡 → 过滤器身份入柜 → Spring 分发），唯一差别：路径 `/note/note/update` 剥前缀后命中 `@PostMapping("/update")`。细节见《发布笔记链路全解剖》第 1~4 步，不重复。

## 第 1 步：校验三连（:435-487）

1. **类型/图片校验**：type=0 图文 ✓，2 张图 ≤8 ✓，拼成 `"aaa.jpg,bbb.jpg"`；
2. **笔记存在性**：`SELECT * FROM t_note WHERE id=1834567890123456` → 查到旧行（creator_id=10001），查不到抛 `NOTE_NOT_FOUND`；
3. **归属校验**（发布没有、修改/删除都有的一道闸）：ThreadLocal 里的 10001 == 该行的 creator_id 10001 ✓ 放行。若是李四来改，≠ 直接抛 `NOTE_CANT_OPERATE`。

**两层防线的概念（面试必背）**：网关是**接口级权限**（你登录了吗、这个接口要不要权限点）；这里是**资源级权限**（这条数据是不是你的）——只有业务层拿着数据才能判。被问"越权改别人笔记怎么拦"，两层都要答。

## 第 2 步：删 Redis 两个 key（:490-492，直连不走 MQ）

- `note_detail:1834567890123456`（详情缓存）
- `published_note_list:10001`（张三主页列表缓存）

**为什么改笔记还要删列表缓存**：列表缓存里存的不是 ID 清单，而是笔记摘要（标题、封面、时间）——主页列表直接展示这些内容。标题/封面变了，不删的话别人看到的就是旧标题旧封面。**原则：笔记的展示信息变了，所有展示它的地方的缓存都要失效。**

## 第 3 步：UPDATE t_note（:496-508，事务内）

`noteDOMapper.updateByPrimaryKey(noteDO)` —— 注意 `noteDOMapper` 是个**没有实现类的接口**，MyBatis 在启动时为它生成代理对象（和 Feign 同一个套路："声明 + 框架生成实现"），调用时去 `NoteDOMapper.xml` 里找同名 SQL 模板，拿 noteDO 的字段值填进 `#{}` 占位符，拼出真实 SQL 再执行：

```sql
UPDATE t_note SET title='我们部门的代码评审经验（2026 修订版）',
                  is_content_empty=0, topic_id=7, topic_name='技术分享',
                  type=0, img_uris='aaa.jpg,bbb.jpg', video_uri=null,
                  update_time='2026-11-20 15:30:00'
WHERE id=1834567890123456;
```

**"全字段无条件更新"的含义**：XML 模板（NoteDOMapper.xml:211-222）里 8 列写死在 SET 里，没有任何 `<if>` 判断——不管 noteDO 里某个字段是不是 null，拼出的 SQL 8 列全更新，null 会把数据库旧值**覆盖成 null**。

对比 `updateByPrimaryKeySelective`：它的模板每个字段外面包着 `<if test="字段 != null">`，拼装时哪个字段是 null 就跳过哪列——只改非空字段，其余列不动（所以删除、置顶这类只翻个别字段的操作用它）。

**两个配套的追问口径**：
- 修改这里为什么敢用全字段版：编辑接口本来就是全量提交，所有字段都赋了值，不存在"误清"；而且"视频笔记改图文"时 videoUri 故意传 null，**就是要借全覆盖把旧视频清掉**——null 覆盖在这里是功能不是 bug。
- Selective 有个天生短板：**它永远没法把字段改成 null**（null 会被跳过）。所以代码里清空 content_uuid 用的是专门手写的 `updateContentUuid(noteId, null)`（:532/:547），这就是证据。

不动的字段：id、creator_id、status、visible、create_time；content_uuid 本例不变（原有正文，复用旧钥匙）。

## 第 4 步：@Transactional 到底包了什么（本链路最重要的机制）

方法头：`@Transactional(rollbackFor = Exception.class)`。它是注解——自己不执行逻辑，是贴给 Spring 的标签。Spring 用代理对象在方法外面包了一层壳，等价于：

```java
connection.setAutoCommit(false);   // 开启事务：之后 SQL 都是"预改"
try {
    updateNote(...)                // 方法体：UPDATE、发消息、调 kv
    connection.commit();           // 正常走完 → 提交，修改真正生效
} catch (Exception e) {
    connection.rollback();         // 抛异常 → 回滚，预改全部作废
}
```

四个必须记住的点：

1. **"先 UPDATE 后调 kv"不等于"元数据先可见"**——commit 发生在方法最后，比 kv 写入还晚。这是一切一致性分析的基石。
2. **回滚靠什么**：MySQL 的 undo log——改数据前自动把旧值抄一份，回滚就是拿抄件还原。进程宕机时连接断开，未提交事务由 MySQL 自动作废，无需代码介入。
3. `rollbackFor = Exception.class`：Spring 默认只对运行时异常回滚，受检异常不回滚——加这个参数堵死默认规则的坑。
4. **自调用失效**：事务逻辑长在代理壳上，同类里 `this.updateNote()` 绕过代理，注解不生效。口诀：注解的功能在代理上，this 调用绕开代理。

## 第 5 步：发两个 MQ 消息（:512、:517）

**5a. 延迟消息（asyncSend）**：`DelayDeleteNoteRedisCacheTopic`，负载 `[1834567890123456, 10001]`，延迟级别 1（1 秒）——延迟双删的闹钟。

**5b. 广播消息（syncSend）**：`DeleteNoteLocalCacheTopic`，负载 `"1834567890123456"`——清所有实例的 Caffeine。

### sync 还是 async：判断标准一句话

> **这条消息丢了，用户会不会立刻看到错的数据、系统能不能接受？** 不能接受 → sync（失败当场抛异常）；能接受、只是幕后清扫 → async（不等回执，回调打日志）。

- **广播删本地缓存用 sync**：本地缓存没清掉，用户刷新立刻看到旧笔记——正确性动作，必须确认送达。而且它在事务里：syncSend 失败抛异常 → 整个事务回滚 → 用户看到"修改失败"重来，绝不允许"用户看到成功但缓存静默没清"。
- **延迟消息用 async**：它是延迟双删的"第二删"，纯保险丝——第一删（第 2 步）已经做了，第二删只在极端并发下才用得上；就算丢了，脏数据等 TTL 到期也自愈。用户已经看到"修改成功"，没理由让主线程为保险丝多等一次网络往返。

### 两个维度，别混（纠正之前"轻重阶梯"的说法）

- **维度一"要不要等 MQ 回执"**：syncSend（等，失败当场抛异常）vs asyncSend（不等，SendCallback 回调打日志）；
- **维度二"消息和数据库要不要原子绑定"**：普通消息 vs 事务消息（半消息+回查）。

本链路广播不需要事务绑定：删缓存是**幂等且方向安全**的操作——多删无害（重建出来的还是正确数据），漏删才有害（sync 已当场抓住）。对比发布的正文消息：消息发了但库回滚 → 孤儿正文（有害！），所以必须事务绑定。**选型口诀：消息消费动作对回滚越有害，越需要事务消息。**

### 这些消息谁来消费？怎么取到消息？

两个 topic 的消费者**都在 note 服务自己内部**（自己发、自己收，不奇怪——消息是给"1 秒后的自己"和"别的实例上的自己"用的）：

| Topic | 消费者类 | 模式 |
|---|---|---|
| DelayDeleteNoteRedisCache | `DelayDeleteNoteRedisCacheConsumer` | 集群模式（默认）：一条消息只被一个实例消费，活干一遍就够 |
| DeleteNoteLocalCache | `DeleteNoteLocalCacheConsumer` | **广播模式**：每个实例都收一份，因为 Caffeine 在各实例自己内存里，必须各删各的 |

**取消息的方式**：消费者代码里只有一个 `onMessage` 方法等框架调用，**感觉上是 MQ 推过来的；底层其实是拉（pull）**——服务启动时，RocketMQ 的客户端 SDK 开后台线程，与 Broker（MQ 服务器）建立一条常驻 TCP 连接，在连接上循环发"长轮询"询问：Broker 有消息立刻回，没消息把请求攥在手里等（超时再回"没有"），SDK 拿到消息就回调 `onMessage`，然后马上发下一个询问。拉模式的好处是消费者按自己的节奏取，不会被 Broker 推过来的消息压垮。

## 第 6 步：同步 Feign 调 kv（:522-540，事务最后一步）

三种情况：

- 改完还有正文 → `saveNoteContent(uuid, 新内容)`：Cassandra 覆盖写（同 uuid 换新内容）；
- 把正文删空了 → `deleteNoteContent(uuid)`：删除正文，成功后把 t_note.content_uuid 置空（:532，避免残留脏指针）；
- 原来没正文这次加了 → 先生成新 uuid 再 save：新增，并把新 uuid 记回 t_note（:547）。

**为什么修改敢同步、发布必须事务消息（核心设计差异）**：修改前存在干净的旧状态（旧元数据+旧正文互相匹配），kv 失败 → 抛异常 → 回滚 MySQL → 两边一起退回旧状态。发布是从无到有，没有旧状态可退，只能保证"存正文任务绝对不丢" → 事务消息。**口诀：能回滚的用本地事务，没法回滚的用可靠消息。**（佐证：发布链路 :162-167 留着被注释的同步 Feign 代码——原作者最初也是同步，后来才改事务消息。）

## 第 7 步：失败全景（四种断点对照）

1. UPDATE 之前断 → 两边都旧 → ✅ 一致
2. UPDATE 后、kv 前断 → MySQL 未提交被作废，kv 没动 → ✅ 都旧
3. kv 成功后、commit 前断 → MySQL 作废（元数据旧），Cassandra 已新 → ❌ 唯一不一致窗口，几毫秒（kv 放最后一步就是为了把窗口压到物理最小；方向固定"元数据旧、正文新"）
4. commit 后断 → kv 早已成功，MySQL 已提交 → ✅ 都新

**诚实边界**：@Transactional 只能回滚 MySQL，Cassandra 写入不参与回滚；彻底消灭窗口需给修改也上事务消息，但有旧状态兜底、频率低，权衡后不值得。

## 第 8 步：返回用户

`Response.success()` → 前端显示"修改成功"。同步段结束。

## 异步段

**⑨ 广播生效（毫秒级）**：所有 note 实例的 `DeleteNoteLocalCacheConsumer`（已核实 `messageModel = BROADCASTING`）收到消息 → 各自 `LOCAL_CACHE.invalidate(noteId)` 清本机内存。本实例自己的 Caffeine 也由这条广播删（广播发给所有实例含自己；:515 注释掉的 `LOCAL_CACHE.invalidate` 证明作者放弃"本机直删"、统一走广播，一条路径管所有实例）。可见性、置顶、删除接口（:617/:695/:736）全复用这套——组合拳复用的又三处证据。

**⑩ 延迟双删第②删（1 秒后）**：`DelayDeleteNoteRedisCacheConsumer` 收到 `[noteId, userId]` → 再删详情缓存 + 列表缓存。
⚠️ 这里是我们发现并修复的真实 bug（4bdfdb4）：原代码第 44 行拼列表 key 时误用 noteId（应为 userId），导致第二次删除永远删一个不存在的 key，延迟双删对列表缓存形同虚设。三条证据：key 构造函数 javadoc 写明 `@param userId`、发布链路传的确实是 creatorId、消费者取出了 userId 却从头到尾没用（取对变量、用错变量）。已一行修复。

**⑪ ES 索引同步（业务代码零参与）**：UPDATE 落库 → MySQL 自动记 binlog（数据库自带流水账）→ Canal（伪装成 MySQL 从库）捕获变更 → search 服务 CanalClient 重建 ES 文档。
**ES 是什么**：专门做全文搜索的数据库。MySQL `LIKE '%关键词%'` 用不上索引全表扫、不会分词、不会相关度排序；ES 用倒排索引（文本拆词 → 建"词→文档列表"反向表），毫秒级命中、支持分词和相关度。定位：MySQL 管"存得准"，ES 管"搜得到"，真相在 MySQL，ES 是搜索优化的副本。
**为什么修改不用发 MQ 通知搜索**：binlog 覆盖一切变更（含直接改库），比显式发事件更全；代价是多维护 Canal 一套组件。

## 数据落点清单

- MySQL t_note：8 个内容字段更新 + update_time（同步，事务内）
- Cassandra note_content：覆盖写/删除（同步 Feign，事务最后一步）
- Redis：`note_detail:{noteId}` + `published_note_list:{userId}` 删除（立即 + 1 秒后第二次）
- Caffeine（所有 note 实例）：广播失效该笔记（毫秒级）
- ES：Canal 监听 binlog 自动重建文档（异步）
- 不动的：t_user_count（修改不影响计数）、t_note_like 等关系表

## 面试官介绍稿（40 秒）

> 修改笔记的核心是三件事：权限、一致性、缓存。权限上除了网关的接口级校验，业务层还有资源归属校验——非作者直接拒绝。一致性上，元数据更新在 @Transactional 本地事务里，Cassandra 正文用同步 Feign 放在事务最后一步，它失败就回滚，两边要么一起新要么一起旧；和发布链路的事务消息是两种方案，因为修改有旧状态可以回滚，发布没有。缓存上是一套组合拳：先删 Redis 详情和列表缓存，延迟一秒补删，再发广播清所有实例的本地缓存。搜索索引不用业务代码管——Canal 监听 binlog 自动同步 ES。

## 深挖追问清单（含口径）

1. **updateByPrimaryKey vs Selective？** → 前者 XML 里 8 列写死全更新、null 会覆盖旧值（修改用，全量提交所以安全，还能借 null 清掉旧视频）；后者 `<if>` 动态只更新非空列（删除/置顶这类窄操作用）
2. **Selective 能把字段改成 null 吗？** → 不能，null 会被 `<if>` 跳过。所以清空 content_uuid 用的是专门手写的 updateContentUuid 语句（:532）——这是项目里的实证
3. **广播消息丢了？** → Caffeine 1 小时 TTL 兜底，错误最多残留一个周期
4. **为什么广播用 syncSend？** → 缓存失效失败必须当场可感知、触发回滚；删缓存幂等无害所以不需要事务绑定。判断标准：这条消息丢了用户会不会立刻看到错数据
5. **延迟消息为什么用 asyncSend？丢了怎么办？** → 第二删是保险丝，丢了脏数据等 TTL 自愈；async 回调只打日志，这里可接受。消息不能丢的场景项目在评论服务里有 SendMqRetryHelper 做本地重试
6. **消费者是怎么拿到消息的，MQ 推的吗？** → 表面是推（写个 onMessage 等回调），底层是拉：SDK 启动后开后台线程，与 Broker 保持一条常驻 TCP 连接，循环发长轮询——有消息秒回，没消息攥到超时再回"没有"。拉模式让消费者按自己节奏消费，不会被压垮
7. **为什么删本地缓存要广播、删 Redis 用集群模式？** → Caffeine 在每个实例自己的内存里，必须每个实例各删各的（广播）；Redis 是共享的，删一遍就够（集群模式一条消息只被一个实例消费）
8. **kv 超时？** → Feign 超时即失败 → 抛异常 → 回滚，用户重试
9. **延迟双删为什么 1 秒？** → 大于一次回源+回填耗时，RocketMQ 预定义延迟档
10. **唯一不一致窗口？** → kv 成功到 commit 之间几毫秒，方向"元数据旧正文新"，kv 放最后压到最小
11. **事务消息为什么不用在修改？** → 有旧状态可回滚，本地事务更简单；事务消息留给"无旧状态可退"的发布。口诀：能回滚的用本地事务，没法回滚的用可靠消息
12. **`#{}` 和 `${}` 区别？** → `#{}` 是 PreparedStatement 安全填参（防 SQL 注入），`${}` 是字符串直接拼接（危险，只在表名/排序字段这种 `#{}` 干不了的地方用）
13. **我们修的 bug？** → 延迟消费者 key 拼错（noteId 误作 userId），三证据确认，一行修复
