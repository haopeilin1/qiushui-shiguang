## 0. 一句话回答（面试可直接用）

**公告既不是笔记，也不是群发给每个用户的消息。**
它的真实模型是：**一份公告只存一行（`t_announcement`）→ 用户自己拉取/打开 → 点"确认已读"才产生一条属于该用户的回执（`t_announcement_read`）→ MQ 异步落库 + Redis 计数 → 管理员查已读率。**

- 发布是 **O(1)**：插一行就结束了，不会循环给 1 万个用户写记录、也不发任何 MQ；
- MQ 里跑的**只有"已读回执"消息**，不是公告内容的分发；
- 公告有**独立的表、独立的权限点、独立的接口**，和 `t_note` 没有关系。

## 1. 三条链路

### 1.1 发布：写一行，结束

```
POST /note/announcement/publish
  → 网关 SaRouter.match("/note/announcement/publish").checkPermission("announcement:publish")
  → AnnouncementServiceImpl.publishAnnouncement
      → Leaf 号段取 announcementId
      → INSERT t_announcement (id,title,content,creator_id,status=0,...)
  → 返回成功
```

关键代码：

```java
String announcementIdStr = distributedIdGeneratorRpcService.getAnnouncementId();
AnnouncementDO announcementDO = AnnouncementDO.builder()
        .id(Long.valueOf(announcementIdStr))
        .title(reqVO.getTitle())
        .content(reqVO.getContent())   // TEXT，最长 10000 字，直接存 MySQL
        .creatorId(creatorId)
        .status(0)
        .build();
announcementDOMapper.insert(announcementDO);
```

**注意三件事：**

1. 没有循环写用户表，也没有 `for (user : allUsers) send()`；
2. 没有发 MQ —— 发布链路一条消息都没有；
3. 正文不走 KV/Cassandra：`content` 是 `TEXT`，因为公告数量少、单条不超过 1 万字，没必要拆。

### 1.2 展示：读扩散（2026-11-20 已补全列表/详情）

当前接口（全部在 `AnnouncementController`）：

| 接口 | 谁能用 | 作用 |
|---|---|---|
| `POST /announcement/publish` | `announcement:publish` | 发布公告（写一行） |
| `POST /announcement/list` | 登录用户 | 分页查生效公告 + isRead + unreadTotal |
| `POST /announcement/detail` | 登录用户 | 查正文 + isRead |
| `POST /announcement/read/confirm` | 登录用户 | 确认已读（Redis SADD 判重 + MQ） |
| `POST /announcement/withdraw` | `announcement:manage` | 撤回（status=1，幂等） |
| `POST /announcement/read/stat` | `announcement:readstat` | 已读率统计 |

列表接口的关键点：

- `selectActivePage`：`where status=0 order by create_time desc, id desc limit ?,?`；
- `isRead` 不逐条查 DB：一次 `SMEMBERS announcement:read:confirm:{userId}` 拿整个已读集合，
  再在内存里 `contains`（Set 不存在时回源 `t_announcement_read` 重建，并回填 7 天 TTL）；
- `unreadTotal`（红点）：一条 `NOT EXISTS` SQL 算完，避免"公告数 - 已读数"在分页时算错。

所以现在是完整的"发布 → 列表 → 详情 → 确认 → 统计 → 撤回"闭环。


### 1.3 确认已读：用户主动触发，每人一条回执

```
POST /note/announcement/read/confirm { announcementId }
  → 校验公告存在且 status=0
  → Redis SADD  announcement:read:confirm:{userId}  member=announcementId
      返回 0 → 已确认过 → 抛 ANNOUNCEMENT_ALREADY_READ
      返回 1 → 首次确认
  → asyncSend("AnnouncementReadTopic", {announcementId,userId,createTime})
      发送失败 → SREM 回滚刚才的判重标记（允许用户重试）
  → 返回成功
```

这里有两个值得说的设计：

1. **用 Set 做判重**：key 是"用户"，member 是"公告 ID"。
   一个用户对多条公告的已读状态，天然聚在一个 Set 里，`SISMEMBER` 还能直接支撑"这个用户读没读这条"。
2. **MQ 发送失败会回滚 SADD**（点赞链路没做这一步）：
   ```java
   public void onException(Throwable t) {
       redisTemplate.opsForSet().remove(readConfirmKey, announcementId.toString());
   }
   ```
   这比"只打日志"更严谨：不会因为一条消息丢了，用户就永远被判"已读"。

### 1.4 消费：落回执 + 维护计数

```
AnnouncementReadConsumer
  → INSERT t_announcement_read
      唯一索引 (announcement_id, user_id) 兜底
      DuplicateKeyException → 视为重复消费，直接 return
  → Redis Hash announcement:read:count:{announcementId} readTotal +1（读改写）
  → EXPIRE 10 分钟（短 TTL，过期后由统计接口回源 DB 重建）
```

### 1.5 统计：读 Redis，miss 回源 DB

```java
Long readTotal = Redis 里 readTotal；
if (读不到) {
    readTotal = announcementReadDOMapper.countByAnnouncementId(id); // SELECT COUNT(*)
    回填 Redis，TTL 10 分钟；
}
Long userTotal = announcementReadDOMapper.countAllUsers(); // t_user where is_deleted=0 and status=0
readRate = readTotal * 100 / max(userTotal,1)，保留 1 位小数
```

## 2. 为什么"不是笔记"？

| 维度 | 笔记 `t_note` | 公告 `t_announcement` |
|---|---|---|
| 内容归属 | 用户创作 | 管理员发布 |
| 正文存储 | Cassandra（content_uuid） | MySQL TEXT（≤10000 字） |
| 发布链路 | 雪花 ID + 事务消息 + KV + 搜索索引 | 号段 ID + 直接 insert |
| 互动 | 点赞/收藏/评论 | 只需"已读确认" |
| 权限 | 登录即可发 | `announcement:publish` |
| 计数 | `t_note_count` | `t_announcement_read` + Redis Hash |

公告是一条**独立的管理类记录**，只是恰好也放在 note 服务里（因为笔记服务和用户关系最近、表也在同一个库）。

## 3. 为什么"不是给每个用户发消息"？——写扩散 vs 读扩散

**写扩散（fan-out on write）**：发布时给每个用户写一条"收件箱"记录。

- 优点：未读数查询极快（`where user_id=? and read=0`）；
- 缺点：1 万员工 × 每条公告 = 1 万行写入；没人看的公告也占空间；发布接口很重。

**读扩散（fan-out on read，本项目）**：公告只存一份，已读回执只在用户确认时写。

- 优点：发布 O(1)；没确认的人不产生任何数据；语义准确（回执 = 确认过，而不是"收到过"）；
- 缺点：查"未读列表/未读数"要做 `公告表 left join 已读表`，比写扩散慢一点。

**为什么本项目选读扩散：**

- 企业公告数量少（一年几百条），员工数有限（万级）；
- 核心诉求是"**谁确认了**"（公文追责），不是"秒级未读红点"；
- 发布接口必须轻，不能因为一次全员公告把数据库写爆。

**数据量估算（1 万员工、一年 200 条公告、确认率 80%）：**

- `t_announcement`：200 行/年，可忽略；
- `t_announcement_read`：1 万 × 200 × 80% ≈ **160 万行/年**，单表完全扛得住，可按年归档；
- Redis：每用户一个 Set（约 160 个 member）≈ 几 KB × 1 万 ≈ 几十 MB；每公告一个计数 Hash，可忽略。

> 如果产品要"打开 App 就有未读红点、且要求毫秒级"，写扩散更合适；
> 如果重点是"公告确认率、谁没确认"，读扩散更简单。这是选型问题，不是对错问题。

## 4. 代码里的细节与坑（面试前务必知道）

### 坑 1：回执 ID 用 `System.currentTimeMillis()`，高并发会主键冲突（已于 2026-11-20 修复）

原实现：

```java
.id(System.currentTimeMillis()) // 记录 ID(够用即可,幂等靠唯一索引)
```

`t_announcement_read.id` 是主键且**没有 AUTO_INCREMENT**。
两个不同用户在同一毫秒确认 → 主键相同 → 抛 `DuplicateKeyException` → 被 catch 当成"重复消费"直接 return →
**回执丢失、计数不加**。

修复：改为雪花 ID（Hutool `IdUtil.getSnowflakeNextId()`），见 `AnnouncementReadConsumer`。

### 坑 2：Redis 判重 Set 没有 TTL，会无限增长（已于 2026-11-20 修复）

原实现只 SADD 不设过期。现在：
- `confirmRead` 成功后给 Set 设 7 天 TTL；
- `list/detail` 回源 DB 重建 Set 时同样设 7 天 TTL。

到期只会让"判重快路径"失效一次，重复确认仍会被 `t_announcement_read` 唯一索引拦住。

### 坑 3：已读计数是"读改写"，并发下会丢更新

因为 Hash value 走 Jackson 序列化，`HINCRBY` 不可用，只能 `get + put`。
并发确认时可能少加。兜底是 10 分钟 TTL 到期后，`readStat` 回源 `COUNT(*)` 修正。

### 坑 4：已读率的分母是"当前全量用户"

`countAllUsers()` 是 `select count(*) from t_user where is_deleted=0 and status=0`。
公告发布之后入职的新员工也会被算进分母，拉低已读率。
真实企业场景应该按"公告的目标人群/发布时在职名单"算——这是产品口径问题，被问到要能说清。

### 坑 5：没有公告列表 / 未读接口（已于 2026-11-20 补全）

已新增 `/announcement/list`、`/announcement/detail`、`/announcement/withdraw`，
前端可以完成"看列表 → 看详情 → 确认已读 → 看红点"的完整流程。

## 6. 面试口径（30 秒）

> "公告不走笔记那套。发布就是往 `t_announcement` 插一行，O(1)，不发 MQ、不循环写用户；
> 用户点确认已读时，才产生一条 `t_announcement_read` 回执：Redis Set 原子判重 → MQ 异步落库
> → 唯一索引兜底 → Redis Hash 维护已读数；统计读 Redis，miss 回源 DB。
> 这是读扩散模型，适合企业内部公告少、员工有限、重点是确认率的场景。
> 如果要做毫秒级未读红点，才考虑写扩散给每人建收件箱。"
