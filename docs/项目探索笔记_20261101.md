## 一、项目整体架构

### 1.1 这是什么

一个企业内部知识分享平台后端，基于 Spring Cloud Alibaba 的微服务系统。
由 **14 个业务微服务** + 1 个公共框架模块（shiguang-framework）+ 1 个压测模块（shiguang-benchmark）组成。

### 1.2 核心概念：微服务到底是什么

- **一个微服务 = 一个独立的 Java 进程**（一个可以单独启动的 Spring Boot 应用）。
- 这些进程可能在同一台电脑上，也可能分布在多台服务器上。
- 即使在同一台电脑上，进程之间也**不能直接互相调用方法**，必须通过 **HTTP 请求**通信。
- 每个服务启动时把自己的地址注册到 **Nacos**（注册中心），其他服务通过 Nacos 找到它。

### 1.3 服务清单与职责

| 服务 | 端口/角色 | 职责 |
|---|---|---|
| shiguang-gateway | 8000，统一入口 | 路由转发、登录认证（Sa-Token）、权限校验 |
| shiguang-auth | 认证 | 登录、验证码、Token 签发 |
| shiguang-user | 用户 | 注册、资料、按 ID 查用户 |
| shiguang-note | 笔记 | 笔记发布/查询/详情聚合 |
| shiguang-kv | KV 存储 | 笔记正文存 Cassandra |
| shiguang-comment | 评论 | 评论增删查 |
| shiguang-user-relation | 关系 | 关注/取关/粉丝列表 |
| shiguang-count | 计数 | 点赞数、粉丝数等，消费 MQ 消息 |
| shiguang-data-align | 数据对齐 | XXL-JOB 定时对账、修正计数 |
| shiguang-search | 搜索 | Elasticsearch 索引与搜索 |
| shiguang-recommend | 推荐 | 个性化推荐 |
| shiguang-agent | AI | 内容理解等扩展 |
| shiguang-oss | 文件 | 图片上传（MinIO/阿里 OSS） |
| shiguang-distributed-id-generator | ID | 分布式 ID 生成 |

### 1.4 api/biz 双模块结构

每个服务拆成两个 Maven 模块：

- **xxx-api**：只放"接口契约"——Feign 接口定义、请求/响应对象（DTO）、常量。**不含业务实现**。
- **xxx-biz**：真正的业务实现——Controller、Service、DAO、消费者。

**为什么要拆**：别的服务要调用 user 服务时，只需依赖 `user-api` 这个轻量模块拿到 Feign 接口，
不需要把 user 服务的全部实现代码（几百个类）引进来。接口和实现解耦。

## 二、服务间通信：Feign 聚合

### 2.1 读请求为什么要"聚合"

以"查看一篇笔记详情"为例，页面需要：笔记内容（note 服务）、作者昵称头像（user 服务）、
点赞数收藏数（count 服务）、正文长文（kv 服务）。这些数据分散在不同进程里，
由 note 服务作为**聚合入口**，分别向其他服务发 HTTP 请求拿数据，拼成一个完整结果返回给前端。

### 2.2 Feign 是什么

**Feign = 把"发 HTTP 请求调用别的服务"伪装成"调用一个本地 Java 方法"的工具。**

以 note 服务调用 user 服务为例，完整链路：

1. 项目启动时，Feign 根据 `UserFeignApi` 接口**自动生成一个代理对象**（不用手写 HTTP 代码）。
2. 调用方写：`userFeignApi.findById(req)`，看起来像普通方法调用。
3. 代理对象在幕后做的事：
   - 把 `req` 对象（DTO）**序列化成 JSON**（对象 → JSON 字符串的过程叫序列化）；
   - 通过 Nacos 查到 user 服务的地址，发 HTTP POST 请求，JSON 放在请求体里；
   - user 服务的 Controller 收到请求，把 JSON **反序列化**回对象（JSON → 对象）；
   - user 查完数据，把结果对象序列化成 JSON 返回；
   - 代理对象收到响应，反序列化成返回值对象，交给调用方。
4. 对调用方来说，整个过程就像调了一个本地方法，HTTP/JSON 细节全被 Feign 藏起来了。

**DTO**（Data Transfer Object，数据传输对象）：专门为服务间传数据定义的类。
比如 `FindUserByIdReqDTO` 只有一个 userId 字段。每个服务的 DTO 字段不同，由接口作者定义。
Feign 和 Spring 内置的 Jackson 库自动完成 JSON 转换，不用手写。

### 2.3 项目里的 6 个 Feign 契约

| Feign 接口 | 提供方 | 主要调用方 | 用途 |
|---|---|---|---|
| UserFeignApi | user | note、comment、relation 等 | 批量查用户昵称头像 |
| KeyValueFeignApi | kv | note | 存/取笔记正文（Cassandra） |
| CountFeignApi | count | note 等 | 查计数，**带 fallback**（count 挂了返回默认值不报错） |
| SearchFeignApi | search | note 等 | 搜索 |
| DistributedIdGeneratorFeignApi | id-generator | 各服务 | 生成分布式 ID |
| FileFeignApi | oss | note 等 | 文件上传 |

**fallback（兜底）**：Feign 支持给接口配一个"失败时用的备胎实现"。目标服务宕机时，
不抛异常，改返回备胎给的默认值（比如计数返回 0），保证主流程不断。

## 三、异步通信：RocketMQ

### 3.1 MQ 是什么

**RocketMQ 是一个独立部署的"消息中转站"进程**（不是变量、不是类、不是数据库）。

- **生产者**（如 user-relation 服务）：把"用户 A 关注了用户 B"这件事打包成一条**消息**，发给 RocketMQ。
- **RocketMQ**：按 **Topic**（主题，相当于消息的分类频道）存起来。
- **消费者**（如 count 服务）：订阅某个 Topic，RocketMQ 把消息推给它处理。

好处：**削峰**（瞬间 1 万个点赞，先堆在 MQ 里慢慢消费，不压垮数据库）和
**解耦**（点赞服务不用知道计数服务的存在）。

### 3.2 广播模式

普通消息：同一条消息只被一个消费者实例处理（竞争消费）。
**广播模式（BROADCASTING）**：同一条消息推给**所有**实例。
项目用它清理本地缓存——每个服务实例内存里都有自己的 Caffeine 缓存，
数据更新后发一条广播消息，**每个实例都收到并清掉自己本地的缓存**。

"确保收信人一定来拿"：MQ 会持久化消息并重试推送，消费者不确认（ACK）成功就一直重试。

### 3.3 顺序消费（ORDERLY）

同一笔记的"点赞→取消→再点赞"必须按顺序处理，否则计数会错。
RocketMQ 支持按某个 key（如笔记 ID）把消息固定路由到同一个队列，保证同 key 消息严格有序。

## 四、多级缓存体系

### 4.1 三级存储结构

一次读请求的查找顺序（以查笔记详情为例）：

```
Caffeine（本进程内存，最快，纳秒级）
   ↓ 没有
Redis（独立进程，内存，网络往返，微秒~毫秒级）
   ↓ 没有
MySQL（独立进程，数据主要落磁盘，毫秒级）
   ↓ 查到后
回填：写入 Redis 和 Caffeine，下次直接命中缓存
```

- **Caffeine**：Java 本地缓存库，数据存在**当前服务进程自己的内存**里。每个实例各有一份，互不可见。
- **Redis**：独立的缓存服务进程，所有微服务实例**共享**同一份数据。数据在内存（带持久化机制）。
- **MySQL**：独立的数据库进程，数据最终落在磁盘，是数据的"源头真相"。

注意：Redis 和 MySQL 是**独立进程但不是微服务**——"微服务"指我们自己写的业务进程；
Redis/MySQL 是现成的**中间件/基础设施**，每个服务需要时去连它们，不是"每个微服务附带一个 Redis"。

### 4.2 项目中的 TTL 明细

**TTL**（Time To Live，存活时间）：缓存条目放进缓存时设置的"过期倒计时"，到期自动删除。
设置时机：**写入缓存那一刻**确定（规则在代码里预先写好，写入时计算，比如加随机值）。

| 数据 | Caffeine | Redis | 设计理由 |
|---|---|---|---|
| 笔记详情 | 1h，上限 1 万条 | 1 天 + 随机 1 天 | 热点读，随机 TTL 防雪崩 |
| 笔记详情空值 | — | 60s + 随机 60s | 防穿透：空值短缓存 |
| 用户信息 findById | 1h | 1 天 + 随机 | 读多写少 |
| 用户主页 profile | 5min | — | 聚合结果，允许短陈旧 |
| 评论 | 1h，1 万条 | — | 同详情 |
| 计数数据 | — | 30min~1h + 随机 | 有过期后回源 count(*) 重建兜底 |
| 验证码 | — | 3min | 安全敏感，短 TTL |
| 公告已读计数 | — | 10min | 过期回源重建 |
| 点赞/关注集合 | — | Lua 中 EXPIRE 1~2 天 | 活跃数据，冷数据自然过期 |
| data-align 布隆过滤器 | — | 20h | 每日重建 |

注意 TTL **只有一层**（规则上写的"1 天+随机"是指生成时加随机偏移，不是两个 TTL）。
所谓"兜底"是指：即使缓存里偶尔有脏数据，TTL 到期后必然回源重查，错误最多残留一个 TTL 周期。

### 4.3 四条设计规律（面试话术）

1. **越热的数据放越近的层级**：详情页读最频繁 → Caffeine+Redis 双级；冷数据直接查库。
2. **TTL = 缓存命中收益与数据陈旧度的权衡**：用户能接受"点赞数晚 10 分钟更新"
   → 计数缓存 TTL 可以长；验证码涉及安全 → 3 分钟必须过期。
3. **随机 TTL 防雪崩**：如果 1 万条缓存同时过期，瞬间全部回源会压垮 MySQL（缓存雪崩）。
   每条 TTL 加随机偏移，过期时间被打散。
4. **空值缓存防穿透**：恶意请求查不存在的 ID，缓存永远 miss，每次都打数据库（缓存穿透）。
   把"查无此数据"这个结果也缓存一小段时间（60s），挡住重复攻击。

### 4.4 布隆过滤器与 Roaring Bitmap

**布隆过滤器（Bloom Filter）**：一个超省内存的"判重"数据结构。
原理：把元素经过几个哈希函数映射到位数组的几个位置置 1；查询时这些位置都是 1 才认为"可能存在"。
特点：**说"不存在"一定准确，说"存在"可能误判**（哈希冲突）；**不支持删除**。

项目中点赞判重的演进：
1. **最初**：点赞记录全查数据库判重，慢。
2. **布隆过滤器**：内存判重，快且省空间，但有两个硬伤——误判（用户没点过却被说点过了）、
   无法取消点赞（位数组不能单独清掉某个元素）。
3. **Roaring Bitmap**（现方案）：一种压缩位图，每个用户 ID 对应一位，精确记录"点过/没点过"，
   **不误判、可取消**，且压缩率高（稀疏数据下远比普通位图省内存）。
   用 Redis 承载，配合 Lua 脚本原子完成"判重+写入"。

### 4.5 缓存一致性：延迟双删 + 广播失效

数据更新时缓存怎么处理？项目方案（以笔记更新为例）：

```
1. 更新 MySQL（先改源头）
2. 删除 Redis 缓存（第一次删）
3. 发一条 MQ 延迟消息，过几百毫秒再删一次 Redis（延迟双删）
4. 发一条 MQ 广播消息，所有实例清掉自己的 Caffeine
```

**为什么要删第二次（延迟双删的时序问题）**：

考虑并发场景：线程 A 更新数据库的同时，线程 B 正在读。
- 时刻1：A 更新数据库为新值
- 时刻2：A 删缓存
- 时刻3：但 B 在时刻1**之前**已经从数据库读了旧值（B 的查询先于 A 的提交），
  时刻3之后 B 才把旧值回填进缓存 → 缓存里又是脏数据了，且数据库已是新值。

第二次延迟删除就是在"等 B 这种慢读请求回填完"之后，再清一次缓存兜底。
**延迟时间定多少**：经验值，要大于"一次读请求回源+回填"的耗时，通常几百毫秒到几秒；
项目用 **RocketMQ 延迟消息**实现（发消息时指定延迟级别，MQ 到点自动投递），不用自己写定时器。

**为什么不用 Canal 监听 binlog 自动清缓存？**
Canal 是伪装成 MySQL 从库、监听 binlog（数据库变更日志）的工具，可以做到"数据一变自动通知"。
但引入 Canal 要多部署一套组件、多一条运维链路；当前延迟双删+广播已能把不一致窗口压到秒级，
且 TTL 兜底保证错误最长残留一个周期——成本收益上不划算。（面试被问可这样答。）

## 五、我们做过的改造与亮点

> 以下为在原有基础上完成的独立工作（dev 分支），简历素材来源。

### 5.1 公告已读回执子域

- 场景：企业内部全员公告，需要确认每个人"已读"，并统计已读率（公文场景）。
- 设计：公告发布、已读确认、已读率统计三个接口，发布/统计仅管理员可用。
- 复用平台互动链路模式：Redis + Lua 原子判重防重复确认，MQ 异步落库，计数服务维护已读数。

### 5.2 消息消费幂等组件（核心亮点）

- **问题**：count 服务 13 个 MQ 消费者没有幂等防护。消息重试、Rebalance（消费者负载重新分配）、
  业务重放都会导致同一事件被消费多次 → 计数多加。
- **方案**：双层防护——
  1. **Redis SETNX 前置判重**：用业务事件 ID（eventId）作幂等键，`SETNX`（不存在才写入）成功才处理，
     说明是首次消费；失败说明重复，直接丢弃。TTL 24h（覆盖 RocketMQ 16 次重试约 4.6h 的窗口）。
  2. **MySQL 唯一索引兜底**：Redis 非持久（可能丢数据），数据库唯一约束是最终防线。
     正常流量 99% 被 Redis 挡住，DB 只承接 Redis 故障期。
- **为什么用 eventId 不用 msgId**：msgId 在重试重投时会变，防不住业务重放；
  eventId 随业务动作生成、稳定不变，且不会误拦"取关后再关注"这类合法新动作。
- **工程化**：模板方法封装，13 个消费者统一接入；开关控制启停（可灰度）。
- **实验证据**：同一业务事件重投 100 次——关闭幂等时粉丝计数 +100，开启后仅 +1。
  （证据文档：`docs/实验证据_幂等对照_20261014.md`）

### 5.3 RBAC 权限与审计

- **RBAC**（Role-Based Access Control，基于角色的访问控制）：用户 → 角色 → 权限点。
- 工作：补全权限点数据，在网关按路由绑定权限校验；管理接口（公告发布、已读统计）仅管理员可用。
- 验证：普通用户越权请求返回 403，管理员正常放行（权限矩阵端到端测试）。
- 审计：operationlog 切面（AOP）自动记录敏感操作日志，串联操作人、参数、结果、请求 ID。
  设计参考等保 2.0 对访问控制与安全审计的要求。

### 5.4 身份透传链（context starter）

- Gateway 统一做登录认证，之后请求在各内部服务间流转时不再重复解析 Token。
- 自研 starter 完成链路：Token 解析 → 用户 ID 写入请求头 → 各服务用 **ThreadLocal**
  （线程私有变量，存当前请求的用户上下文）绑定 → Feign 调用下一服务时自动把请求头续传下去。
- 效果：业务服务代码里零 Token 解析逻辑，直接取上下文即可。

### 5.5 修复的缺陷

- 笔记详情页作者信息误显示为当前登录用户（取错上下文），并清理了相关缓存污染。
- 已读计数 Hash 在 JSON 序列化下 HINCRBY 不可用，改为读改写 + 短 TTL 防脏计数。
- 5 张表补 AUTO_INCREMENT、starter SPI 包名修正等本地联调修复。

## 七、词汇表

| 缩写/术语 | 全称/含义 |
|---|---|
| TTL | Time To Live，缓存存活时间 |
| MQ | Message Queue，消息队列 |
| DTO | Data Transfer Object，服务间传数据的 Java 类 |
| HTTP | 进程间通信的网络协议，微服务之间靠它通话 |
| JSON | 一种文本数据格式，对象↔文本的转换叫序列化/反序列化 |
| API | 接口，一个服务对外提供的能力清单 |
| Feign | 把 HTTP 调用伪装成本地方法调用的 Java 库 |
| Nacos | 注册中心+配置中心，服务启动时登记地址，互相查找靠它 |
| Rebalance | MQ 消费者扩容/缩容时的负载重新分配，期间消息可能重复投递 |
| binlog | MySQL 记录所有数据变更的日志文件 |
| Canal | 监听 binlog 做数据同步的开源组件 |
| RBAC | 基于角色的访问控制 |
| AOP/切面 | 在不改业务代码的前提下，统一给一批方法加日志/权限等横切逻辑 |
| XXL-JOB | 分布式定时任务平台，支持把任务分片到多台机器并行跑 |
| ACK | 消费者告诉 MQ"这条消息我处理完了"的确认 |
| 幂等 | 同一操作执行一次和执行 N 次结果相同 |
| SETNX | Redis 命令：key 不存在才写入，天然判重 |
| 缓存穿透 | 查不存在的数据，缓存 miss 直打数据库 |
| 缓存雪崩 | 大量缓存同时过期，请求瞬间全打数据库 |
| 熔断降级 | 依赖的服务挂了时快速失败/返回兜底数据，不把线程堵死（Sentinel） |

## 九、换设备部署指引

```bash
git clone <仓库地址>
cd qiushui-shiguang
git checkout dev   # 我们的改造都在 dev 分支
```

需要自备的中间件（配置均指向 127.0.0.1 本地）：
MySQL、Redis、Nacos、RocketMQ（可选：Elasticsearch、Canal、MinIO）。

- `sql/` 目录有建库脚本
- `run/` 目录有启动脚本
- 启动顺序参考 README：基础中间件 → id-generator → kv → user → auth → oss → note →
  count → comment → user-relation → search → recommend → agent → gateway
- 阿里云 SMS/OSS 密钥通过环境变量注入（配置里全是占位符，无需改代码）
