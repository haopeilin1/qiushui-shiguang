# 请求入口链路全解剖：从前端发请求到 publishNote 被调用

> 整理日期：2026-11-25
> 范围：一个 HTTP 请求从浏览器发出，到 note 服务的 Controller 方法被 JVM 执行之间的**全部环节**。
> 原则：每个环节都对着项目真实代码讲；所有追问过的细节均已收录。
> 示例：张三（userId=10001）发笔记，POST `/note/note/publish`。

---

## 0. 前置背景：Token 是哪来的

张三昨天登录过：auth 服务校验密码通过后，**Sa-Token 框架干了两件事**：

1. 生成一个随机字符串 `f4a9c2e1...` 作为 Token 返回给张三（前端之后每次请求都带上）；
2. 往 Redis 写入一条映射：key = `Authorization:login:token:f4a9c2e1...`，value = `10001`（张三的 userId）。

**关键认知：Token 本身不含任何信息，它就是一把钥匙；"钥匙对应谁"这个信息存在 Redis 里。**
所以只要 Token 有效，必然能查出 userId——key 是钥匙，value 就是 userId，同一条记录。

---

## 1. 全链路一图流（先看全貌）

```
浏览器 ──Token(Header)+JSON(body)──> 网关 :8000
   ① SaReactorFilter：免验名单? → checkLogin() 查 Redis，无效→401 打回
   ② AddUserId2HeaderFilter：Token→Redis 查 userId → 请求头盖章 userId:10001
   ③ 路由(application.yml)：/note/** 命中 → StripPrefix=1 剥成 /note/publish
      → lb://shiguang-note 去 Nacos 查实例地址 → HTTP 转发到 192.168.x.x:8090
        │
        ▼
   note 服务（Tomcat 内嵌于进程中）
   ④ Tomcat：收字节 → 按 HTTP 协议拆成 HttpServletRequest 对象 → 线程池拨线程
   ⑤ HeaderUserId2ContextFilter（项目代码）：取 header 的 userId → 存 ThreadLocal
      → chain.doFilter() 交棒
   ⑥ DispatcherServlet（Spring）：查映射表 POST+/note/publish → 命中 publishNote
   ⑦ InvocableHandlerMethod（Spring）：备参数（Jackson 把 body JSON → PublishNoteReqVO，
      @Validated 校验）→ Method.invoke(controller单例, vo) ← 反射在这里！
   ⑧ NoteController.publishNote(vo) → noteService.publishNote(vo)（普通调用，无反射）
      → Service 里随时 LoginUserContextHolder.getUserId() = 10001
   ⑨ 返回后：过滤器 finally 里 remove() 清 ThreadLocal；Jackson 把返回值转 JSON 原路返回
```

## 2. 第一站：前端发请求

```
POST http://47.100.x.x:8000/note/note/publish
Authorization: Bearer f4a9c2e1...
Content-Type: application/json

{"type":0, "title":"代码评审经验", "content":"……", "imgUris":["a.jpg"], "topicId":7}
```

两类信息分开放：

- **Header 里的 Token**："我是谁"——注意 **userId 从头到尾不出现在 body 里**。前端自报"我是 10001"不可信，身份只能由网关验票后盖章；
- **body 里的 JSON**："我要干什么"。

8000 端口是网关，所有请求的唯一入口。

## 3. 第二站：网关 · SaReactorFilter（验票）

代码：`shiguang-gateway/.../auth/SaTokenConfigure.java`

```java
SaRouter.match("/**")                        // 拦所有路径
        .notMatch("/auth/login")             // 免验名单：登录、验证码、热搜等少数接口
        .notMatch("/auth/verification/code/send")
        ...
        .check(r -> StpUtil.checkLogin())    // 其余一律验登录
```

执行顺序（钉死）：

1. 看路径在不在**免验名单** → 在 → 跳过登录校验直接放行；
2. 不在 → `checkLogin()`：拿 Token 去 Redis 查，无效/过期 → 抛 NotLoginException，**401 打回，请求到此为止**；
3. （少数管理接口额外 `checkPermission` 查权限点——这是简历第 5 条 RBAC 在网关的落点；发笔记不需要权限点。）

这一关回答的问题："**你登录了吗？**"（接口级权限。资源级权限——"这条数据是不是你的"——在业务层，两边配合才完整。）

## 4. 第三站：网关 · AddUserId2HeaderFilter（身份盖章）

代码：`shiguang-gateway/.../filter/AddUserId2HeaderFilter.java`

```java
// 1. 从请求头取 Token，去掉 "Bearer " 前缀
String token = tokenValue.replace("Bearer ", "");
// 2. 拼 Redis key 查 userId
Integer userId = redisTemplate.opsForValue().get("Authorization:login:token:" + token);
// 3. 查到了 → 把 userId 塞进请求头，转发给下游
exchange.mutate().request(builder -> builder.header(GlobalConstants.USER_ID, "10001"));
```

**这是整个身份传递的核心**：网关把"不可信的前端自报身份"换成"网关验票后亲手盖在请求头上的章"。从此请求头多了一行 `userId: 10001`，下游所有服务只信这个章。

### 追问 1：这里是不是查了两次 Redis？

**是，概念上两次查的是同一条记录。**

- `checkLogin()`（Sa-Token 内部）：查 Token 存在且未过期——关心"钥匙有效吗"；
- `AddUserId2HeaderFilter`：用同一个 key（前缀 `Authorization:login:token:`）再查一次——目的是把 value（userId）读出来用。

确实可以优化（第一次查完暂存给第二次用，省一次网络往返），项目没做。面试主动指出这是加分项。

### 追问 2：为什么查不到 userId 也放行？

**职责分离：这个过滤器的职责是"盖章"，不是"守门"。** 守门是第①步的事——Token 无效在 checkLogin 就被 401 打回了，理论上到不了这里。"查不到也放行"是防御性写法，兜两种边角：

- **免验接口**：`/auth/login` 等根本没 Token，不能在这里被拦；
- **时序缝隙**：checkLogin 刚验过、这里查之前 Token 恰好过期被删——放行下去，下游 ThreadLocal 没有 userId，业务取不到身份会按未登录处理，**出错但不会出错事**（不会把张三当李四）。

原则一句话：**每个组件只拦自己职责内的坏人；放行不代表信任，下游还有兜底。**

## 5. 第四站：网关 · 路由转发

配置：`shiguang-gateway/src/main/resources/application.yml`

```yaml
routes:
  - id: note
    uri: lb://shiguang-note          # lb = load balance，去 Nacos 找名叫 shiguang-note 的服务
    predicates:
      - Path=/note/**                # URL 以 /note 开头 → 走这条
    filters:
      - StripPrefix=1                # 剥掉第一段路径前缀
```

三步：

1. **匹配**：`/note/note/publish` 命中 `Path=/note/**`；
2. **剥前缀**：`StripPrefix=1` 切掉第一段 `/note`，转发出去的 URL 变成 **`/note/publish`**。这就是前端路径比 Controller 注解多一段的原因；
3. **找地址**：`lb://shiguang-note` 不是真实地址。网关拿服务名去 **Nacos** 查活着的实例列表，多个实例就负载均衡挑一个。

### 追问：转发的请求什么样？端口不变吗？

**路径剥第一段，其余原封不动**（HTTP 方法、body、所有 header 含新盖的 userId、query 参数全保留）；**但 host 和端口变了，而且必须变**——网关自己是 8000，它要把请求发给 Nacos 查到的真实实例，实际发出的是：

```
POST http://192.168.1.5:8090/note/publish
```

网关在这里的角色是**反向代理**：对外只有一个门面 8000，对内换成真实干活的地址；前端永远不需要知道 note 服务在哪。

## 6. 第五站：note 服务 · Tomcat（拆协议 + 分线程）

### Tomcat 到底是什么（纠正常见误解）

**Tomcat 不是一个线程，是一整个 Web 服务器，而且就住在 note 服务这个 Java 进程里面**（Spring Boot 把它打进 jar，不用单独安装）。Tomcat 内部维护一个**线程池**（默认约 200 个线程），每来一个请求拨一个线程处理。"Tomcat 分配线程"是这个服务器的动作。

### "解析 POST"的两层分工（重要）

请求到达时本质是一串字节：

```
POST /note/publish HTTP/1.1
Host: 192.168.1.5:8090
Authorization: Bearer f4a9c2e1...
userId: 10001
Content-Type: application/json
（空行）
{"type":0,"title":"代码评审经验",...}
```

- **第一层：Tomcat 解析"协议"**。把这串字节按 HTTP 格式拆开：第一行拆出方法+路径+协议版本，下面逐行拆 header，空行后是 body。包装成 `HttpServletRequest` 对象。**注意：body 在这一层还是"生肉"——一段没动过的原始文本，Tomcat 不关心它是不是 JSON。**
- **第二层：Jackson 解析"数据"**（在后面的第 8 站）：把 body 那段 JSON 文本填成 VO 对象。

比方：Tomcat 是邮局分拣员，拆信封、登记收件人寄件人（header）、抽出信纸（body）但不读信；Jackson 是翻译官，负责读信纸内容。

## 7. 第六站：note 服务 · HeaderUserId2ContextFilter（身份入柜）

代码：`shiguang-framework/.../filter/HeaderUserId2ContextFilter.java`（公共模块，每个服务都有）

```java
String userId = request.getHeader(GlobalConstants.USER_ID);   // 取 header 里的 "10001"
if (StringUtils.isBlank(userId)) { chain.doFilter(request, response); return; }  // 没有则放行
LoginUserContextHolder.setUserId(Long.valueOf(userId));        // 放进 ThreadLocal
try {
    chain.doFilter(request, response);                          // 交棒，继续往 Controller 走
} finally {
    LoginUserContextHolder.remove();                            // 请求结束务必删除
}
```

### ThreadLocal 是什么

**"线程私有的小柜子"**。处理这个请求的线程，在其整个生命周期里，任何代码任何地方调 `LoginUserContextHolder.getUserId()` 都能拿到 10001——不用层层方法传参。这就是为什么 Controller/Service 的方法签名里没有 userId，业务代码却随时能取（如修改笔记的归属校验）。

### 追问 1：放 ThreadLocal 是 Tomcat 做的吗？

**不是。** Tomcat 只提供线程（场地和工人）；放 ThreadLocal 是**项目自己写的过滤器代码**干的，只是这段代码跑在 Tomcat 拨的线程上。

### 追问 2：finally 里的 remove() 为什么必须写？

线程是**池化复用**的——这个请求处理完，线程还给池子接待下一个请求。不擦掉的话，下一个请求会读到张三残留的 userId，**串号**。"用完必删"是铁律。

### 补充（你可能没问但会卡住）：为什么用 TransmittableThreadLocal 而不是普通 ThreadLocal？

`LoginUserContextHolder` 里用的是 `TransmittableThreadLocal`（TTL，阿里开源）。普通 ThreadLocal 的值只存在当前线程；一旦代码里用了**线程池异步任务**（比如 CompletableFuture 并行调 RPC），任务被提交到**另一个线程**执行，普通 ThreadLocal 的值就丢了。TTL 能在任务提交时把值"传递"到执行线程。笔记详情页并行调 user/kv 的 RPC 就靠它保证 userId 不丢。

### `chain.doFilter(request, response)` 是谁写的？

**这行代码本身是项目过滤器里的（人写的）；但它调下去之后发生的事全是框架的。** `chain` 对象由 Tomcat 创建并传入，`doFilter()` 的意思是"把接力棒交回链条"：后面还有过滤器就调下一个；过完了就到 Spring 的 DispatcherServlet。**不写这行 = 接力棒断在手里，请求永远到不了 Controller**——新手写过滤器最常踩的坑。

### 接力赛全景：每一棒是谁写的

| 棒次 | 干什么 | 谁写的 |
|---|---|---|
| Tomcat | 收字节、拆协议、建 request 对象、建过滤器链 | Tomcat |
| 过滤器（们） | 存 ThreadLocal，然后 chain.doFilter() 交棒 | **项目代码**（你唯一能看见的一棒） |
| DispatcherServlet | 查映射表 | Spring |
| InvocableHandlerMethod | 备参数（Jackson）+ 反射调用 | Spring |
| publishNote 方法体 | 业务逻辑 | **项目代码** |

## 8. 第七站：Spring 分发（查表 + 备参 + 反射调用）

### 前置：映射表是什么时候建的？

note 服务启动时，`main` 方法里 `SpringApplication.run(...)` 执行，Spring 启动（几秒钟），期间：

1. **扫描**：按包名扫所有类，找贴了 `@RestController`/`@Service`/`@Component` 等注解的；
2. **建对象（IOC）**：给这些类各 new 一个实例放进容器（默认**单例**，全应用就一份），并注入依赖（`@Resource private NoteService noteService` 就是这时被填上的）；
3. **建映射表**：把每个 Controller 的类级 `@RequestMapping` + 方法级 `@PostMapping` 拼起来登记：
   ```
   {POST /note/publish} → NoteController实例.publishNote 方法（存的直接是 Method 对象/书签）
   {POST /note/update}  → ...
   ```
4. 最后启动内嵌 Tomcat，监听端口。**这些全部发生在接收第一个请求之前。**

### NoteController 的真实形态

```java
@RestController              // 我是接 HTTP 请求的类，返回值由 Jackson 转 JSON 当响应体
@RequestMapping("/note")     // 类级公共前缀
public class NoteController {

    @Resource
    private NoteService noteService;   // 启动时被注入单例

    @PostMapping("/publish")           // → 拼起来：POST /note/publish
    public Response<?> publishNote(@Validated @RequestBody PublishNoteReqVO vo) {
        return noteService.publishNote(vo);
    }
    // 类上前缀 + 方法后缀 = 完整路径；启动时 Spring 据此建"URL→方法"内存表
}
```

### 请求到来时的三步（全部在 Spring 内部）

以 `POST /note/publish` 为例：

1. **查表**：DispatcherServlet 拿"POST + /note/publish"当 key 查映射表 → 命中 publishNote（key 是方法+路径的组合，因为同路径不同 HTTP 方法可能对应不同 Java 方法）；
2. **备参数**：`InvocableHandlerMethod.getMethodArgumentValues()` 遍历方法签名，看到 `@RequestBody` → 调 Jackson 把 body JSON 逐字段填成 `PublishNoteReqVO`（这就是"反序列化"：文本 → 内存对象）；看到 `@Validated` → 顺手触发 VO 里的规则校验（如 `@NotNull`），不合格当场返回错误，方法体不执行；
3. **反射调用**（下一节细讲）：`method.invoke(controller单例, vo)`。

## 9. 反射：刨开 jar 包看到的真身

### 反射不在你的代码里

`noteService.publishNote(vo)` 这行**没有反射**，是普通调用（你写代码时就知道方法名，编译期焊死）。反射只出现在"**Spring → 你的 Controller**"这一跳——所以你在项目源码里永远看不见它，它在 spring-web 的 jar 包里。

### 为什么这一跳非反射不可

Spring 的 `DispatcherServlet` 是框架作者很多年前写好的代码，它的任务是"调用户的 Controller 方法"，但**它诞生时你的 publishNote 根本不存在**，不可能把你的方法名写死进代码。没有反射只有两条死路：

- 写死调用 → 不可能预知用户的方法名；
- 强制用户实现统一接口（如都叫 handle()）→ 用户自己写 if-else 分发 URL，@PostMapping 这种优雅机制不存在（早期 Servlet 年代真这样）。

有了反射，分发器只需一个通用套路：**查表 → 拿 Method 对象 → method.invoke(实例, 参数)**，不管方法叫什么都能调。

### 实物证据：InvocableHandlerMethod（spring-web-6.0.4.jar）

反编译还原出的核心代码：

```java
public Object invokeForRequest(NativeWebRequest request, ...) {
    Object[] args = getMethodArgumentValues(request);   // 先备料（Jackson 填 VO 在这里）
    return doInvoke(args);
}

protected Object doInvoke(Object... args) throws Exception {
    Method method = getBridgedMethod();        // 取出启动时存好的 Method 书签
    return method.invoke(getBean(), args);      // ← 反射本体，就这一行
}
```

- `getBridgedMethod()`：启动时建表阶段从你的 NoteController.class 捞出并存好的 `Method` 对象；
- `getBean()`：从 IOC 容器取 NoteController 单例；
- `method.invoke(bean, args)`：把"书签+对象+参数"递给 JVM。

**注意分工：映射表里存的是现成的 Method 书签，请求来了是"取"不是"找"；"找到位置"是启动时扫描建表干的，反射管的是"最后那一下调用"。**

### 反射为什么能运行它不认识的方法

你写的 .java 编译成 .class（字节码），启动时 JVM 加载进内存，每个方法在内存里都有一份指令，`Method` 对象就是指向那段指令的**书签**。`method.invoke(bean, args)` 翻译给 JVM 听就是："去书签指的位置开始执行指令，这个对象当 this，这些当参数。"**真正执行代码的是 JVM，Spring 只负责递书签**——它不需要知道你方法内部怎么写。播放机（JVM）放你录好的视频（字节码），Spring 只是按了播放键。

### 面试口径

> DispatcherServlet 拿请求查 HandlerMapping 里启动时注册的映射，找到 HandlerMethod，由 RequestMappingHandlerAdapter 交给 InvocableHandlerMethod：先用参数解析器处理 @RequestBody（Jackson 反序列化成 VO），最后通过 Method.invoke 反射调起 Controller 单例的方法。

## 10. 第八站：Controller → Service（转交）

```java
return noteService.publishNote(vo);
```

"转交"就是**一次最普通的方法调用**。`noteService` 是成员变量，启动时 Spring 通过 `@Resource` 把单例 Service 对象填进来（依赖注入）。同一个线程顺着这次调用走进 Service 方法，几百行业务逻辑在同一个线程里接着跑。

### 三层架构（Service 是什么）

| 层 | 职责 | 比方 |
|---|---|---|
| Controller | 接请求、收参数、返回响应 | 前台接待 |
| Service | 业务逻辑（校验、决策、编排） | 办事的 |
| Mapper | 跟数据库打交道（MyBatis） | 跑库房的 |

好处：业务逻辑不跟 HTTP 搅在一起（MQ 消费者、定时任务也能复用 Service）；出问题好定位。

### 配套概念一：IOC / 依赖注入（区别于反射！）

- **IOC 管"对象哪来"**：启动时统一 new 好所有对象放容器（默认单例），类里只声明"我需要一个 NoteService"（@Resource），Spring 自动填入。好处：对象只建一份、依赖集中管理、换实现不用改使用方。
- **反射管"不知道名字怎么调用"**：框架编译期不知道用户的方法名，运行时拿 Method 对象现场调。

口诀：**表管"记着位置"，IOC 管"备好对象"，反射管"最后那一下调用"**——三者接力，缺一不可。

### 配套概念二：单例共享为什么不会串数据

所有请求共享一个 Service 单例，但方法里用的是**局部变量**（每个线程自己一份），成员变量只有 Mapper、RedisTemplate 这些线程安全工具。所以 userId 这种"每个请求都不同"的数据**绝不能**存成 Service 成员变量——这正是要用 ThreadLocal 的原因，设计在此闭环。

### 补充（没问过但易卡）：VO 和 DTO 的区别

项目里前端→服务传的叫 **VO**（View Object，如 PublishNoteReqVO），服务间 Feign 传的叫 **DTO**。本质一样，都是"数据包裹单"，只是使用场景不同叫法不同。

## 11. 第九站：返回与收尾

- Service 返回结果 → Controller 包装成 `Response.success()`；
- `@RestController` 作用下，Jackson 把返回对象**序列化**成 JSON → HTTP 响应原路返回（来去的同一条路，方向相反）；
- 过滤器 finally 里 `LoginUserContextHolder.remove()` 清柜；
- 线程还给 Tomcat 线程池，等待下一个请求。

## 12. 概念速查表（面试随时调取）

| 概念 | 一句话 | 在本链路的位置 |
|---|---|---|
| 注解 | 贴给框架看的标签，本身没逻辑 | @PostMapping、@RequestBody、@Resource |
| Token（Sa-Token） | Redis 登录态的钥匙，本身无信息 | 网关验票 + 盖章 |
| 反向代理 | 对外一个门面，对内转发真实地址 | 网关 8000 → 各服务 |
| 路由 + StripPrefix | 按路径分发 + 剥前缀 | /note/note/publish → /note/publish |

## 13. 面试实战问答（本条链路可能被问的）

1. **"一个请求从进来到业务代码，中间经历了什么？"**
   → 按一图流讲：网关验票查 Redis → 盖章 userId 进 header → 路由剥前缀 + Nacos 查址转发 → Tomcat 拆协议建 request → 过滤器存 ThreadLocal → Spring 查映射表 → Jackson 反序列化 → 反射调 Controller → 转交 Service。
2. **"用户身份怎么传递的？"**
   → Token 是 Redis 登录态的钥匙；网关验票后把 userId 盖到请求头；下游公共过滤器把头里的 userId 存进 TransmittableThreadLocal；业务随时取，用完 finally 删。**前端传的 userId 我们不认，身份只信网关盖的章。**
3. **"ThreadLocal 为什么要 remove？为什么会内存泄漏？"**
   → 线程池复用，不删会串号；ThreadLocalMap 的 key 是弱引用、value 是强引用，线程不死 value 不释放 → 内存泄漏。
4. **"为什么用 TransmittableThreadLocal？"**
   → 普通 ThreadLocal 在线程池异步任务（如 CompletableFuture 并行调 RPC）时值传不过去，TTL 能在任务提交时传递。
5. **"网关鉴权和业务里的归属校验什么关系？"**
   → 两层防线：网关是接口级（登录没、接口要什么权限点），业务层是资源级（这条数据是不是你的）——只有业务层拿着数据才能判。
6. **"反射是什么？项目里哪里用了？"**
   → 运行时拿 Method 对象动态调方法。框架编译期不知道用户方法名，Spring MVC 分发、IOC 建对象、MyBatis/Feign 生成代理实现，底层都是反射/动态代理。实物：InvocableHandlerMethod 的 `method.invoke(getBean(), args)`。
7. **"Controller 调 Service 为什么不是反射？"**
   → 那是用户自己写的代码，编译期方法名就焊死了，直接调用。反射只在"框架调用户代码"的边界上。
