## 0. 30 秒版（面试可直接背）

点赞接口同步只做三件事：**校验笔记存在 → Redis Lua 原子判重并写入点赞状态 → 发一条顺序 MQ 后立刻返回**。

真正的落库和计数全在 MQ 后面：
1. `LikeUnlikeNoteConsumer` 顺序消费 `LikeUnlikeTopic`，`insertOrUpdate` 写 `t_note_like`；
2. 落库成功后转发 `CountNoteLikeTopic`；
3. 计数服务用 BufferTrigger 把 1 秒内的消息按 `noteId` 聚合，先 `HINCRBY` 更新 Redis 计数 Hash；
4. 再发 `CountNoteLike2DBTTopic` 批量写 `t_note_count` 和 `t_user_count`；
5. `data-align` 用布隆过滤器记录"今天哪些 noteId 变过"，XXL-JOB 分片 `count(*)` 回源校准。

一句话：**同步只写 Redis（快、原子、可判重），异步落 DB 与计数（削峰、解耦），定时任务兜底（最终一致）。**

### 1.1 "点赞成功"到底完成了什么（同步 / 异步边界）

先记住一句话：**接口返回的"成功"，语义是"Redis 里的点赞状态已经原子翻转过来了 + 消息已经交给本地发送线程"，
不是"数据库已经落库"，更不是"broker 已经收到"。**

**同步段（返回前必须做完）**

| 顺序 | 动作 | 代码 | 是否一定碰 Redis/DB |
|---|---|---|---|
| 1 | 校验笔记存在并拿作者 ID | `checkNoteIsExistAndGetCreatorId` | 通常只读 Caffeine/Redis；两者都 miss 才查 DB |
| 2 | 原子判重 + 置位 | `rbitmap_note_like_check.lua` | 1 次 Redis（Lua 内 3 条命令） |
| 3 | 维护"最近 100 条点赞" | `note_like_check_and_update_zset.lua` | 1 次 Redis；**ZSet 不存在时会同步查一次 DB 最近 100 条**并批量重建 |
| 4 | 生成 eventId、拼消息 | `LikeUnlikeNoteMqDTO.builder().eventId(UUID...)` | 纯内存 |
| 5 | 异步投递消息 | `asyncSendOrderly(..., hashKey=userId)` | 只是交给本地发送线程，**不等 broker ACK** |
| 6 | 返回 | `return Response.success()` | 无 data，只有 success=true |

**异步段（返回之后才发生）**

| 时机 | 动作 | 谁做的 |
|---|---|---|
| 返回后几十 ms | 消息真正发到 broker；失败只打日志 | RocketMQ 客户端线程 |
| 毫秒级 | 写 `t_note_like`（`insertOrUpdate`），成功后转发计数消息 | `LikeUnlikeNoteConsumer` |
| ~1 秒 | 按 noteId 聚合 +1/-1，`HINCRBY count:note:{id}` / `count:user:{id}` | `CountNoteLikeConsumer`（BufferTrigger） |
| ~1 秒后 | 事务更新 `t_note_count` / `t_user_count` | `CountNoteLike2DBConsumer` |
| 同时 | 布隆判重 + 写当天临时表（供对账） | `TodayNoteLikeIncrementData2DBConsumer` |
| 当天/定时 | `count(*)` 校准 MySQL 计数、Redis、ES 文档 | XXL-JOB 分片任务 |
| 异步 | 更新用户兴趣画像 | `UserInterestByLikeConsumer`（推荐服务） |

**所以用户点完赞立刻刷新会看到什么？**

- "已赞"状态：**立刻正确**（详情页/`isLikedAndCollectedData` 读的就是 bitmap）；
- 点赞数：**可能还是旧值**，约 1 秒后才 +1（读的是 `count:note:{id}` 这个 Redis Hash，由计数消费者更新）；
- 搜索页/推荐页里的点赞数：更晚，要等对账后重建 ES 文档。

**同步段里唯一可能明显变慢的地方**：ZSet 或 bitmap 不存在时的"冷启动重建"——会同步查一次 DB。
这也是为什么第一次点赞偶尔比后面慢。

**每个环节的失败影响（面试常问"哪一步挂了会怎样"）**


| 失败点 | 现象 | 兜底 |
|---|---|---|
| Redis 写失败 | 接口直接报错，用户重试即可 | 无脏数据 |
| MQ 发送失败 | 接口仍返回成功；Redis 说已赞，DB 无记录、计数没加 | 只能等 bitmap TTL（1~2 天）回源修复；这是当前设计最弱的一环 |
| 关系落库消费失败 | MQ 重投；`insertOrUpdate` 覆盖写，天然幂等 | RocketMQ 重试 |
| 计数聚合失败 | Redis 计数少加 | data-align 定时校准 |
| 计数落库失败 | DB 计数偏差 | data-align 定时校准 |
| ES 未更新 | 搜索页计数旧 | 对账任务重建文档 |

## 1.2 异步六步到底在干什么（逐段拆解）

### 第 1 步：消息真正发到 broker（返回后几十 ms）

- **做什么**：`asyncSendOrderly` 只是把消息交给 RocketMQ 客户端的本地发送线程；这个线程再通过 Netty 把消息发到 broker，
  成功后 broker 把它写进 CommitLog 落盘。
- **代码**：`rocketMQTemplate.asyncSendOrderly(destination, message, hashKey, callback)`，回调里只 `log.info` / `log.error`。
- **为什么不等**：等 broker ACK 会把接口 RT 从"几次 Redis 往返"拉长到"一次网络 + 磁盘写"，而且 broker 抖动会直接让点赞失败。
- **失败后果**：broker 不可用 → 回调 `onException` 打日志，消息丢，接口依然返回成功。
  这时 Redis 说"已赞"、DB 没记录，只能等 bitmap TTL（1~2 天）回源修复。

> 这一步之后，消息才真正"安全"（broker 落盘）。之前它只存在于笔记服务的发送队列里，进程一挂就没了。

### 第 2 步：写点赞关系表，再转发计数消息（毫秒级）

- **做什么**：`LikeUnlikeNoteConsumer` 按 `userId` 顺序消费：
  1. 解析消息，构造 `NoteLikeDO`（`status = type`，1=点赞 0=取消）；
  2. 点赞走 `insertOrUpdate`，取消走 `update2Unlike...`；
  3. **只有 affected rows > 0 才转发** `CountNoteLikeTopic`。
- **SQL 语义**：
  - 点赞：`INSERT ... ON DUPLICATE KEY UPDATE create_time=?, status=?`；
  - 取消：`UPDATE ... SET status=0 WHERE user_id=? AND note_id=? AND status=1`。
- **为什么用 affected rows 做闸门**：重复投递时行状态没变，MySQL 返回 0，就不发计数消息 ——
  等于在"关系表"这一层又做了一次幂等，避免重复 +1。
- **失败后果**：消费抛异常 → RocketMQ 重投；因为写的是"覆盖状态"而不是"累加"，重投天然安全。

### 第 3 步：Redis 计数聚合（约 1 秒）

- **做什么**：`CountNoteLikeConsumer` 用 BufferTrigger 攒一批（最多 1000 条 / 1 秒）：
  1. 反序列化，按 `noteId` 分组；
  2. 组内 `LIKE +1 / UNLIKE -1` 求和，得到净变化；
  3. `HINCRBY count:note:{noteId} likeTotal 净变化`；
  4. 同时 `HINCRBY count:user:{creatorId} likeTotal 净变化`。
- **关键细节：先 `hasKey` 再 INCR**。
  计数 Hash 有 TTL（约 30min~1h+随机），过期后由"查询计数"接口回源 DB `count(*)` 重建。
  如果消费者对已过期的 key 直接 INCR，会造出一个"只有增量、没有基数"的脏 Hash（比如显示点赞数=1，实际 1 万）。
- **为什么在这里聚合**：1000 次行更新压成 1 次 Redis 操作；Redis 单 key 的 INCR 是原子且极快。
- **失败后果**：这一批 Redis 更新丢了 → 计数偏小；读接口回源 DB 或第 6 步对账会修回来。

### 第 4 步：MySQL 计数落库（约 1 秒后）

- **做什么**：`CountNoteLike2DBConsumer` 消费 `CountNoteLike2DBTTopic`，对每个聚合项开一个编程式事务：
  ```sql
  INSERT INTO t_note_count (note_id, like_total) VALUES (?, ?)
    ON DUPLICATE KEY UPDATE like_total = like_total + (?);   -- 笔记维度

  INSERT INTO t_user_count (user_id, like_total) VALUES (?, ?)
    ON DUPLICATE KEY UPDATE like_total = like_total + (?);   -- 作者维度
  ```
- **为什么用事务**：两张表必须同时成功/同时失败，否则会出现"笔记点赞数加了、作者获赞数没加"。
- **注意这里是"增量"不是"绝对值"**：所以一旦某条消息丢了或重复，DB 计数会偏 —— 这正是第 6 步要用绝对值覆盖的原因。
- **失败后果**：事务回滚 → MQ 重投 → 重复加；靠第 5 步记下"这个对象变过"，第 6 步用 `count(*)` 覆盖修正。

### 第 5 步：记录"今天哪些对象变过"（与第 3 步同时）

- **做什么**：`TodayNoteLikeIncrementData2DBConsumer` 也订阅 `CountNoteLikeTopic`（独立消费组），但**不记数字，只记 ID**：
  1. 用当天布隆过滤器判断 `noteId` 今天是否已记录；
  2. 没记录 → 插入 `t_data_align_note_like_count_temp_{yyyyMMdd}_{noteId % shards}`；
  3. 插入成功后 `BF.ADD`；
  4. 再对 `creatorId` 做一遍，写入 `t_data_align_user_like_count_temp_...`。
- **为什么只存 ID**：这是一张"待对账清单"，不是计数表。对账时要的是"哪些对象可能不准"，具体数字现场 `count(*)` 算。
- **为什么用布隆**：一篇爆款笔记一天可能被点赞几万次，不去重就会往临时表插几万行；
  布隆把写入量从"事件数"降到"对象数"（每篇笔记每天一行）。
- **顺序为什么不能反**：先写库、后 `BF.ADD`。如果先加布隆再写库，写库失败后这个对象当天就再也不会被记录 → 永久漏对账。
- **临时表谁建的**：`CreateTableXxlJob` 每天提前创建"明天"的各分片表；`DeleteTableXxlJob` 定期清理一个月前的表。
- **失败后果**：临时表少记一个对象 → 这次对账漏掉它；等它下次发生变化会重新入表，属于"延迟修复"。

### 第 6 步：XXL-JOB 分片对账（当天/凌晨）

以 `NoteLikeCountShardingXxlJob` 为例（`UserLikeCountShardingXxlJob` 同理，只是维度换成作者）：

1. 取分片参数：`shardIndex` / `shardTotal`，拼出自己负责的表 `..._temp_{昨天}_{shardIndex}`；
   > 注意：消费者写的是**今天**的表，任务读的是**昨天**的表 —— 因为当天数据还在变，凌晨跑"昨天完整一天"的账更稳。
2. 循环：每次取 1000 个 `noteId`，取不到就结束；
3. 对每个 `noteId` 执行真相查询：
   ```sql
   select count(*) from t_note_like where note_id = ? and status = 1
   ```
4. **用绝对值覆盖**：`update t_note_count set like_total = ? where note_id = ?`；
5. 如果 Redis 里 `count:note:{noteId}` 存在，`HSET likeTotal = 真实值`（也是覆盖，不是 INCR）；
6. 调搜索服务 `rebuildNoteDocument(noteId)`，让 ES 文档里的点赞数跟着更新；
7. 删除这一批已处理的临时表记录，继续下一批。

作者维度（`UserLikeCountShardingXxlJob`）的真相查询是：

```sql
select count(*) from t_note_like
where status = 1
  and note_id in (select note_id from t_note where creator_id = ?)
```

然后覆盖 `t_user_count.like_total` 和 Redis `count:user:{userId}` 的 `likeTotal`（ES 文档里存的是笔记维度计数，所以这一步不重建文档）。

- **为什么用绝对值**：增量链路一旦错一次，后面所有增量都在错误基数上累加；`count(*)` 是"从真相重算"，能把历史错误一起清掉。
- **为什么要分片**：临时表按 `id % table.shards` 分了多张，XXL-JOB 的多个执行器各领一张表并行跑，避免单机扫全表。
- **为什么处理完要删**：任务可中断、可重跑；崩了下次从剩下的记录继续，不会重复处理。
- **失败后果**：某个对象对账失败 → 记录还在临时表，下次任务继续；最坏情况是当天没修，等它下次变更再修。

### 六步速查表

| 步骤 | 输入 | 输出 | 失败兜底 |
|---|---|---|---|
| 1 发 broker | 内存消息 | broker CommitLog | 无（会丢，靠 TTL/对账） |
| 2 写关系表 | `LikeUnlikeTopic` | `t_note_like` + 计数消息 | MQ 重投 + 覆盖写幂等 |
| 3 Redis 计数 | `CountNoteLikeTopic` | `count:note/user` Hash | 读接口回源 DB / 对账 |
| 4 MySQL 计数 | 聚合消息 | `t_note_count` / `t_user_count` | 事务回滚 + 对账覆盖 |
| 5 记变更对象 | `CountNoteLikeTopic` | 临时表（只有 ID） | 下次变更再入表 |
| 6 分片对账 | 昨天临时表 | 三处绝对值和 ES | 记录保留，下次继续 |

### 2.2 校验笔记存在（三级缓存）

```java
private Long checkNoteIsExistAndGetCreatorId(Long noteId) {
    String json = LOCAL_CACHE.getIfPresent(noteId);          // Caffeine
    FindNoteDetailRspVO vo = JsonUtils.parseObject(json, FindNoteDetailRspVO.class);
    if (Objects.isNull(vo)) {
```

### 2.3 Lua 判重 + 写入（核心中的核心）

`NoteServiceImpl#likeNote`：

```java
String rbitmapKey = RedisKeyConstants.buildRBitmapUserNoteLikeListKey(userId); // rbitmap:note:likes:{userId}
DefaultRedisScript<Long> script = new DefaultRedisScript<>();
script.setScriptSource(new ResourceScriptSource(new ClassPathResource("/lua/rbitmap_note_like_check.lua")));
script.setResultType(Long.class);

Long result = redisTemplate.execute(script, Collections.singletonList(rbitmapKey), noteId);
NoteLikeLuaResultEnum luaResult = NoteLikeLuaResultEnum.valueOf(result);
```

`rbitmap_note_like_check.lua` 全文（19 行，值得背）：

```lua
local key = KEYS[1]
local noteId = ARGV[1]

-- 1. bitmap 是否存在
local exists = redis.call('EXISTS', key)
if exists == 0 then return -1 end

-- 2. 这一位是否已经是 1
local isLiked = redis.call('R.GETBIT', key, noteId)
if isLiked == 1 then return 1 end

-- 3. 没点过 -> 置 1（判重和写入在同一个原子单元里）
redis.call('R.SETBIT', key, noteId, 1)
return 0
```

返回码语义（Java 侧 `NoteLikeLuaResultEnum` 分支）：
- `-1`：bitmap 不存在 → 回源 `t_note_like` 判断，并按需异步全量重建 bitmap；
- `1`：已点赞 → 抛 `NOTE_ALREADY_LIKED`；
- `0`：本次是首次点赞，且**已经原子置位**。

> 注意：`R.SETBIT` 不是普通 `SETBIT`，是 RedisBloom / Redis Stack 提供的 Roaring Bitmap 命令；
> key 是一张压缩位图，`noteId` 当偏移量，1 篇笔记占 1 bit。

### 2.4 ZSet：只维护"最近 100 条点赞"

判重靠 bitmap，但个人主页"我赞过的笔记"需要按时间排序，所以还有一份 ZSet：

`note_like_check_and_update_zset.lua`：

```lua
local exists = redis.call('EXISTS', key)
if exists == 0 then return -1 end

local size = redis.call('ZCARD', key)
if size >= 100 then redis.call('ZPOPMIN', key) end  -- 只留最近 100 条
redis.call('ZADD', key, timestamp, noteId)
return 0
```

ZSet 不存在时，Java 侧查 `selectLikedByUserIdAndLimit(userId, 100)` 用
`batch_add_note_like_zset_and_expire.lua` 重建，再补一次当前点赞。

**bitmap 与 ZSet 的分工**（面试高频）：
- bitmap 回答"**有没有点过赞**"，O(1)、极省内存、可取消；
- ZSet 回答"**最近赞了哪些、按时间排序**"，用于列表展示，容量受控（100）。

### 2.5 发 MQ：顺序消息 + tag

```java

        .type(LikeUnlikeNoteTypeEnum.LIKE.getCode()) // 1
        .createTime(now).noteCreatorId(creatorId)
```

3. 发送失败只记日志 —— 这是"MQ 挂了点赞还能成功吗"的答案来源。

### 2.7 计数第一跳：BufferTrigger 聚合

`CountNoteLikeConsumer`：

2. 组内 `LIKE` 就 +1、`UNLIKE` 就 -1，得到净变化 `finalCount`；
3. `redisTemplate.opsForHash().increment("count:note:{noteId}", "likeTotal", finalCount)`；

5. 把聚合结果发到 `CountNoteLike2DBTTopic` 落库。

注释写得很清楚：Hash 有 TTL，过期后由"查询计数"接口回源 DB 重建，避免消费端把过期缓存又写出来一个只有增量、没有基数的脏 Hash。

## 3. 追问逐条（面试现场版）

### Q1：为什么用 Lua？不用 Lua，用 Java check-then-set 会怎样？

Java 写法通常是两次 Redis 调用：

```java
Boolean liked = redisTemplate.opsForValue().getBit(key, noteId); // 第一次网络往返
if (!liked) {
    redisTemplate.opsForValue().setBit(key, noteId, true);       // 第二次网络往返
    // 发 MQ、计数 +1
}
```

问题有两个：

1. **并发窗口**：两个请求几乎同时 `GETBIT` 都拿到 0，然后都 `SETBIT`，都认为自己是首次点赞 → 两次 MQ、计数 +2。加 `synchronized` 只能管住单机，多实例部署照样穿透。
2. **多次 RTT**：判重 + 写入至少 2 次网络往返，点赞是高频接口，延迟翻倍。

Lua 方案：Redis 执行脚本时是**单线程、不可被其他命令插入**的，`EXISTS → GETBIT → SETBIT` 三条命令作为一个整体执行，天然是"比较并设置（CAS）"语义，并发下只有一个请求能拿到 `return 0`。

补充两个容易被追问的点：
- Redis 的原子性只保证"脚本执行期间不插入别的命令"，**不保证脚本里多个 key 的事务回滚**（Lua 中途报错，前面的写不会撤销）。所以脚本要写得足够简单、参数校验前置。
- Redis Cluster 下，一个 Lua 脚本涉及的所有 key 必须在同一个 slot。项目里每个脚本只操作一个 key，所以没有这个问题。

### Q2：Lua 脚本里具体做了哪几步？返回值怎么用？

同步链路上其实有 **3 个 Lua**：

| 脚本 | 作用 | 返回码 |
|---|---|---|
| `rbitmap_note_like_check.lua` | 判重 + 置位（点赞的原子入口） | `-1` bitmap 不存在 / `1` 已赞 / `0` 首次成功 |
| `rbitmap_add_note_like_and_expire.lua` | bitmap 刚初始化时补当前 bit + 设 TTL | `0` |
| `note_like_check_and_update_zset.lua` | 维护最近 100 条点赞 ZSet | `-1` ZSet 不存在 / `0` 成功 |

取消点赞用 `rbitmap_note_unlike_check.lua`：

```lua
local exists = redis.call('EXISTS', key)
if exists == 0 then return -1 end
local isLiked = redis.call('R.GETBIT', key, noteId)
if isLiked == 0 then return 0 end          -- 没赞过，不能取消
return redis.call('R.SETBIT', key, noteId, 0)  -- 返回旧值 1，表示取消成功
```

注意最后一行：`R.SETBIT` 返回的是**修改前的旧值**。旧值是 1 才说明这次取消有效，Java 侧据此判断。

Java 侧不是 `if (result == 1)`，而是用枚举把返回码翻译成业务分支：

```java
switch (NoteLikeLuaResultEnum.valueOf(result)) {
    case NOT_EXIST -> { /* 回源 DB + 异步重建 bitmap */ }
    case NOTE_LIKED -> throw new BizException(ResponseCodeEnum.NOTE_ALREADY_LIKED);
    case SUCCESS -> { /* 继续 */ }
}
```

### Q3：判重到底用什么结构？Set / Hash / ZSet？

**都不是，主体是 Roaring Bitmap**（`R.SETBIT` / `R.GETBIT`），ZSet 只是辅助的"最近列表"。

演进过程（这条线很适合讲"为什么这么选"）：

1. **最初：查 DB 判重** —— 每次点赞一条 `select count(*) from t_note_like`，高频写下 DB 直接成瓶颈。
2. **布隆过滤器** —— 内存小、O(1)，但两个硬伤：有假阳性（没赞过可能被判赞过）、**不支持删除**（位数组不能单独清 0），所以取消点赞做不了。项目里还留着 `bloom_note_like_check.lua` 等历史脚本。
3. **Roaring Bitmap（现方案）** —— 精确、可置 0（能取消）、压缩率高。key 按用户维度：`rbitmap:note:likes:{userId}`，用 noteId 当 offset。

为什么按 userId 建 key 而不是按 noteId？
- 点赞接口要回答的是"**这个用户有没有赞过这篇**"，按用户建 key 一次 `GETBIT` 就够；
- 如果按 noteId 建 key，一个爆款笔记的位图会非常大（用户 ID 稀疏、跨度大），压缩率反而差；
- 按用户建 key 的代价是：查"这篇笔记被谁赞过"不方便 —— 但产品上没有这个需求，列表走 DB/ES。

内存估算（面试常问）：1 亿用户，每人平均点赞 500 篇、noteId 分布稀疏，Roaring Bitmap 压缩后大约每用户几 KB 到几十 KB；再配 1~2 天 TTL，只有活跃用户常驻。

### Q4：为什么不同步写库？"降低同步写库压力"具体指什么？

同步写要落两张表：`t_note_like`（关系）+ `t_note_count`（计数），而且计数是**同一行热点**：一篇爆款笔记的所有点赞都在更新 `t_note_count` 的同一行，行锁会把并发打回串行。

异步方案的三层收益：

1. **接口 RT**：同步只写 Redis（内存操作 + 1 次 MQ 投递），不等 MySQL；
2. **削峰 + 合并**：BufferTrigger 把 1 秒内最多 1000 条消息按 noteId 合并成 1 次 `HINCRBY`，1000 次行更新变成 1 次；
3. **解耦**：笔记服务不需要知道计数服务的表结构，计数服务挂了也不影响点赞接口返回。

代价（一定要主动说，否则显得只会背优点）：
- 计数是最终一致，详情页可能秒级延迟；
- 需要额外的对账/补偿链路（data-align、XXL-JOB、ES 重建）；
- 链路变长，排查问题要跟 MQ TraceId。

### Q5：MQ 用的是普通消息还是顺序消息？hashKey 怎么选的？

**关系落库链路用顺序消息**，**计数链路用普通消息**，这是差异化的设计。

```java
// 关系落库：顺序 + 异步
asyncSendOrderly("LikeUnlikeTopic:Like", message, String.valueOf(userId), callback);

// 计数：普通 + 异步（在 LikeUnlikeNoteConsumer 里发）
asyncSend("CountNoteLikeTopic", message, callback);
```

`hashKey = userId` 的理由：
- 需要保序的是"**同一个用户对同一篇笔记的连续动作**"：赞 → 取消 → 再赞。这三条只要进了同一队列，就一定按发送顺序消费，DB 最终状态正确、计数净变化正确。
- 为什么不用 `noteId`？用 noteId 也能保证同一篇笔记有序，但一篇爆款笔记的所有用户的点赞会挤进**同一个队列**（热点队列），顺序消息本来就是单队列串行，吞吐会被打到极低。用 userId 能把流量打散到所有队列。
- 反过来说，用 userId 时"不同用户对同一篇笔记"是无序的 —— 这没关系，因为计数是求和（+1/-1 可交换），关系表是按 `(user_id, note_id)` 各自一行，互不干扰。

计数链路为什么可以无序？
- 消息在 `CountNoteLikeConsumer` 里先按 noteId 分组、再做 `+1/-1` 求和，**加法可交换**，顺序不影响 `finalCount`；
- `HINCRBY` 也是原子增量，顺序无关。

顺序消息的代价（要能说出来）：
- 单队列串行消费，消费能力受单线程限制；
- 所以 `LikeUnlikeNoteConsumer` 加了 `RateLimiter(5000/s)` 做削峰，消费不过来就让 MQ 堆着；
- Rebalance 期间可能重复投递，靠 `insertOrUpdate` / `update2Unlike` 的幂等兜住。

### Q6：取消点赞和点赞乱序了怎么办？

分三层回答：

1. **正常情况下不会乱序**：`asyncSendOrderly` + `hashKey=userId`，同一用户进同一队列，`ConsumeMode.ORDERLY` 顺序消费。
2. **即使乱序，关系表最终状态也对**：
   - 点赞 `insertOrUpdate(status=1)`，取消 `update ... set status=0 where status=1`；
   - 两条消息谁后到，谁的 `status` 生效，"最后写入者赢"，这就是业务上的正确语义；
   - 重复取消时 `affected rows=0`，直接 return，不会重复发计数消息。
3. **计数不怕乱序**：`+1/-1` 求和可交换，先减后加和先加后减结果一样。

真正需要担心的是"**丢**"而不是"乱"（见 Q7）。

顺带对比关注链路（`RelationServiceImpl.follow`）：它做了和点赞一样的 `asyncSendOrderly(hashKey=userId)`，
但**额外生成了 `eventId = UUID.randomUUID()`** 放进消息体，下游 `FollowUnfollowConsumer` 再原样透传给计数消息 ——
这是第 4 条幂等组件的前置条件。点赞消息体 `LikeUnlikeNoteMqDTO` 里**没有 eventId**，这个差异第 4 节会讲。

### Q7：Redis 里的计数和 DB 不一致怎么办？

先分类，再给兜底：

| 场景 | 后果 | 兜底 |
|---|---|---|
| Redis 有状态、DB 无记录（MQ 丢消息） | 用户被判"已赞"，DB 没行、计数没加 | bitmap TTL 1~2 天后回源 DB 自动修复；期间用户取消再赞可恢复 |
| DB 有记录、Redis 无状态（Redis 重启/过期/被清） | 判重点 miss | 回源 `selectByUserId` 全量重建 bitmap，结果正确 |
| Redis 计数偏差 | 详情页点赞数不准 | data-align 每日临时表 + XXL-JOB `count(*)` 校准 |
| ES 计数偏差 | 搜索页/推荐页不准 | 对账任务完成后调搜索服务重建文档 |

对账为什么用 `count(*)` 而不是"把增量补上"？
因为增量链路一旦错过一条，后面所有增量都是在错误基数上累加；`count(*)` 是**从真相表重新算**，能把历史错误一起清掉。代价是每天要对 `t_note_like` 做一次统计，所以用"当天变更过的 ID"（布隆去重的临时表）+ 分片并行来把范围缩到最小。

### Q8：MQ 挂了，点赞还能成功吗？消息丢了怎么办？

**接口会成功返回。** 因为 `asyncSendOrderly` 只是把消息交给本地发送线程，回调异常只打日志：

```java
public void onException(Throwable throwable) {
    log.error("==> 【笔记点赞】MQ 发送异常: ", throwable);
}
```

所以 broker 不可用时的真实结果：Redis 位图已经置 1 → 用户看到"已赞"，但 `t_note_like` 没记录、计数没加。

这是**可用性优先**的取舍：点赞是弱一致性业务，丢一条不值得让接口报错。兜底只有两条：
1. bitmap TTL 到期后回源 DB，状态自动纠正（最长 1~2 天）；
2. 用户取消再点赞，会重新走一遍链路。

面试时主动给出改进方案（体现你知道问题在哪）：
- **本地消息表（outbox）**：点赞时在同一个本地事务里写一条"待发送"记录，定时任务补发，最稳；
- **RocketMQ 事务消息**：项目里发笔记 (`PublishNoteTransactionTopic`) 就是这么做的，点赞链路没用；
- **发送失败同步回滚 Redis bit**：实现简单，但回滚也可能失败，且会把"已赞"状态闪断，不推荐作为主方案；
- **失败重试 + 告警**：至少让丢消息可观测，而不是只在日志里。

## 4. 代码里的坑（面试前必须知道，别被追问翻车）

> **2026-11-19 更新：坑 1 / 2 / 3 / 4 已经在代码里修掉了**，具体改动见本节末尾的《修复清单》。

### 坑 1：`t_note_like` 没有唯一索引，但代码用了 `ON DUPLICATE KEY UPDATE`（已修复）

`sql/01_schema.sql`：

```sql
CREATE TABLE `t_note_like` (
  ...
  PRIMARY KEY (`id`),
  KEY `idx_user_note` (`user_id`, `note_id`),   -- 普通索引，不是 UNIQUE
  KEY `idx_note_id` (`note_id`)
)
```

而 `NoteLikeDOMapper.xml` 的 `insertOrUpdate` 是：

```sql
INSERT INTO t_note_like (user_id, note_id, create_time, status)
VALUES (...)
ON DUPLICATE KEY UPDATE create_time = ..., status = ...
```

没有唯一键，`ON DUPLICATE KEY` **永远不会触发**，每次点赞都会插一条新行；取消点赞的 `update ... where status=1` 会一次改多行（MySQL 会全部更新），`affected rows` 也不等于 1。

**建议**（面试前改掉，或者至少心里有数）：

```sql
ALTER TABLE t_note_like
  ADD UNIQUE KEY uk_user_note (user_id, note_id);
```

注意：补唯一索引前要先清历史重复数据，否则建索引会失败。

### 坑 2：`status` 的注释和代码是反的（已修复）

schema 注释写的是 `0-有效 1-已取消`，但代码里：

- `LikeUnlikeNoteTypeEnum`：`LIKE(1)`、`UNLIKE(0)`；
- 所有查询 `selectCountByUserIdAndNoteId` / `selectByUserId` / `selectLikedByUserIdAndLimit` 都是 `status = 1` 表示"已点赞"。

所以真实语义是 **1=有效点赞，0=已取消**。注释需要改，否则面试官看 SQL 会以为你连字段含义都没搞清。

### 坑 3：简历说"13 个消费者补齐幂等"，代码里只接了一个（已修复）

`shiguang-count` 里 13 个消费者是：

```

CountNoteCollectConsumer / CountNoteCollect2DBConsumer / CountNoteCommentConsumer /
CountNoteChildCommentConsumer / CountCommentLikeConsumer / CountCommentLike2DBConsumer /
CountFollowingConsumer / CountFollowing2DBConsumer / CountFansConsumer / CountFans2DBConsumer
```

但全仓库搜 `DedupService`，**只有 `CountFansConsumer` 真正注入了它并调用 `isDuplicate`**。
其余 12 个消费者没有任何幂等判重（关系落库端靠 `insertOrUpdate` 的覆盖写，计数端靠对账）。

**口径建议**（二选一）：
- 保守说法："幂等组件以粉丝计数消费者为样板完成了接入和对照实验，其余消费者按同一模板推广"——诚实且能讲清设计；
- 或者面试前真的把其余消费者接上（模式很固定：在 `onMessage` 入 BufferTrigger 之前解析 DTO、拼 bizKey、`isDuplicate` 拦截）。但"13 个都验证过"这种话，没有对应代码就别说了。

### 坑 4：点赞消息没有 `eventId`，幂等键只能退化（已修复）

`LikeUnlikeNoteMqDTO` 字段只有 `userId / noteId / type / noteCreatorId / createTime`，**没有 eventId**。
关注链路的 `FollowUserMqDTO` 才有 `eventId(UUID)`。

后果：如果给点赞消费者接 `DedupService`，只能退化成 `topic:userId:noteId:type` 键，
这正好是 `docs/实验证据_幂等对照_20261014.md` 里 v1 踩过的坑 —— **"取消后再点赞"会被残留键误拦**。

正确做法：在 `likeNote`/`unlikeNote` 构造 DTO 时加 `eventId = UUID.randomUUID().toString()`，
并让 `LikeUnlikeNoteMqDTO` 增加该字段（下游 `CountNoteLikeTopic` 复用同一个消息体，天然透传）。

### 坑 5：`NOTE_LIKED` 分支有一段被注释掉的 DB 二次校验

`NoteServiceImpl#likeNote` 里，Lua 返回"已点赞"时，原代码有一段（已注释）：

```java
// Double score = redisTemplate.opsForZSet().score(userNoteLikeZSetKey, noteId);
// if (Objects.nonNull(score)) throw new BizException(NOTE_ALREADY_LIKED);
// int count = noteLikeDOMapper.selectNoteIsLiked(userId, noteId);
// if (count > 0) { asynInitUserNoteLikesZSet(...); throw ... }
```

说明作者考虑过"Redis 说赞过、其实 DB 没有"的情况。面试可以主动提：
"这里如果做 DB 二次校验能提高准确率，但会给点赞接口增加一次 DB 查询，所以当前选择了性能优先，靠 TTL 自愈。"

### 坑 6：`DedupService` 注释写 7 天，实现是 24 小时（已修复）

接口 javadoc 里写 `SET bizKey 1 NX EX 7d`，`DedupServiceImpl` 里是 `Duration.ofHours(24)`。
被问到 TTL 时以**实现为准（24h）**，理由：RocketMQ 默认 16 次重试总窗口约 4.6 小时，24h 已有 5 倍冗余。
（2026-11-19 已把注释改成 24h。）

```java
// 业务事件级：优先 eventId（重投 / 业务重放都稳定）

// 消息级：同一个 Topic 被多个消费组订阅时，用消费者类名区分，避免互相误杀
```

## 5. 一页速记（考前 3 分钟）

| 项 | 值 |
|---|---|
| 接口 | `POST /note/like`、`/note/unlike`、`/note/collect` |
| 判重结构 | Roaring Bitmap：`rbitmap:note:likes:{userId}`，noteId 当 offset |
| 判重 Lua | `rbitmap_note_like_check.lua`：EXISTS → R.GETBIT → R.SETBIT，返回 -1/1/0 |
| 取消 Lua | `rbitmap_note_unlike_check.lua`：R.SETBIT 0，返回旧值 |
| 最近列表 | ZSet `user:note:likes:{userId}`，最多 100 条 |
| TTL | 1 天 + 随机 0~1 天（防雪崩） |
| 关系 MQ | `LikeUnlikeTopic:Like` / `:Unlike`，`asyncSendOrderly`，hashKey=userId |
| 关系消费者 | `LikeUnlikeNoteConsumer`，ORDERLY + RateLimiter 5000/s |
| 关系表 | `t_note_like`，status 1=有效 0=取消，`insertOrUpdate` / `update2Unlike` |
| 计数 MQ | `CountNoteLikeTopic`（无序，聚合求和） |
| 计数聚合 | BufferTrigger：50000 / 1000 条 / 1s，按 noteId 求和 |
| 计数缓存 | `count:note:{noteId}`、`count:user:{creatorId}` 的 `likeTotal` |
| 计数落库 | `CountNoteLike2DBTTopic` → 事务更新 `t_note_count` + `t_user_count` |
| 对账 | data-align 临时表 + 布隆 + XXL-JOB 分片 `count(*)` |
| 最弱一环 | MQ 发送失败只打日志，Redis 已置位 → 等 TTL 自愈 |

## 6. 这条的主线逻辑（一句话 + 钩子）

**同步只做"能快速失败、能原子判重"的事，所有"慢、重、可延迟"的事都丢给 MQ，再用对账兜住 MQ 兜不住的部分。**

面试时讲到"计数落库"就停，留半句钩子：
> "计数的写路径是异步聚合的，但读路径其实还有一套缓存设计 —— 详情页的点赞数不是每次都查 DB 的，这就要说到 Caffeine + Redis 两级缓存了。"

这样下一题自然就切到**第 2 条：多级缓存**。
