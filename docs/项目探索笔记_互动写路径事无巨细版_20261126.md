> 配套文档：《第1条_互动写路径_20261119.md》（含对账六步与坑清单），本文以"一条动作走完全程"的视角组织。

## 0. 一句话总览（30 秒版）

> 点赞、收藏、关注三个接口的同步部分都不碰数据库：先进 Redis，用 Lua 脚本原子地完成"判重 + 写入"（点赞/收藏用 Roaring Bitmap 记录关系、ZSet 记录列表；关注用 ZSet 记录关注列表），然后发一条 RocketMQ 顺序消息就返回成功。落库和计数全在异步段：关系消费者把点赞关系写进 MySQL（唯一索引兜底幂等），再转发计数消息给计数服务；计数服务先做幂等判重（Redis SETNX + 业务事件 ID），再用 BufferTrigger 把 1 秒内的消息聚合成批次，批量更新 Redis 计数，最后异步落 MySQL。Redis 和 DB 之间是最终一致，由 data-align 服务的 XXL-JOB 定时对账兜底。

## 1. 点赞链路（主解剖对象）

### 第 1 步：入口（同入口链路文档，不重复）

`POST /note/note/like`，body 只有 `{"id": 1834567890123456}`。网关验票盖章 → note 服务 → `NoteController.likeNote(LikeNoteReqVO vo)` → `NoteServiceImpl.likeNote`（:758）。

**注意：同步部分从这里开始，全程不碰 MySQL 的写。**

### 第 2 步：校验笔记存在 + 拿作者 ID（:763）

`checkNoteIsExistAndGetCreatorId(noteId)`——查笔记详情（走三级缓存：Caffeine → Redis → MySQL），顺便拿到作者 `creatorId=10002`（后面消息体要用，计数时给作者加赞数）。

### 第 3 步：Lua 脚本原子判重 + 写入 Roaring Bitmap（:770-811，核心中的核心）

Redis key：`note_service:rbitmap:user_note_like:10001`（张三的点赞位图）。

**先解释 Roaring Bitmap 是什么**：一种压缩位图。给每个笔记 ID 分配一个 bit，点过赞 = 1，没点 = 0。一个用户点赞 10 万篇笔记也只占约 12KB 级别的内存（稀疏时压缩效率极高）。判重就是查一个 bit，O(1)，比查 Set/数据库快得多。

执行的 Lua 脚本 `rbitmap_note_like_check.lua`，逐行翻译：

```lua
local exists = redis.call('EXISTS', key)     -- 位图存在吗？
if exists == 0 then return -1 end            -- 不存在 → 返回 -1（NOT_EXIST）

local isLiked = redis.call('R.GETBIT', key, noteId)  -- 查这个 noteId 对应的 bit
if isLiked == 1 then return 1 end            -- 已是 1 → 返回 1（已点赞，判重拦截）

redis.call('R.SETBIT', key, noteId, 1)       -- 是 0 → 置 1（写入）
return 0                                     -- 返回 0（本次点赞成功）
```

**为什么必须用 Lua（面试必考）**："查一下 bit、没有就置 1"是两步操作。如果用 Java 代码先 GETBIT 再 SETBIT，两次 Redis 往返之间，同一个用户的另一个请求（比如双击、重试）可能插进来，两个请求都读到 0，都置 1，都以为自己是第一次——**重复点赞**。Lua 脚本在 Redis 里**整体原子执行**（Redis 执行脚本期间不处理其他命令），把"查+写"焊成一步，从根上杜绝并发缝隙。

Java 侧拿到返回值后分三种情况（:786-834）：

- **`0`（成功）**：继续往下走；
- **`1`（NOTE_LIKED）**：抛 `NOTE_ALREADY_LIKED` 异常，前端提示"已赞过"——判重在这里生效；
- **`-1`（NOT_EXIST，位图不存在，比如缓存过期了）**：回源数据库查 `t_note_like`：
  - DB 里有记录 → 说明赞过，**异步**重建位图（线程池 `threadPoolTaskExecutor.submit`），抛"已赞过"；
  - DB 里没有 → **同步**从 DB 把该用户所有点赞记录灌进位图并设随机过期（保底 1 天 + 随机 0~1 天，防缓存雪崩），再执行 `rbitmap_add_note_like_and_expire.lua` 把这次点赞写进去。

### 第 4 步：更新 ZSet 点赞列表（:836-877）

Redis key：`note_service:user_note_like_zset:10001`——张三"我赞过的笔记"列表，ZSet 结构（member=noteId，score=时间戳，按时间排序天然支持"最近赞过的在前"）。

执行 `note_like_check_and_update_zset.lua`：

```lua
if EXISTS == 0 then return -1 end   -- 列表缓存不存在 → 返回 -1
if ZCARD >= 100 then ZPOPMIN end    -- 只保留最近 100 条，超了踢掉最早的
ZADD key timestamp noteId           -- 写入本次点赞
```

**为什么只留 100 条**：个人主页"我赞过的"列表是低频长尾数据，100 条以外的用 DB 分页兜底，缓存只抗热点。若返回 -1（ZSet 不存在），从 DB 查最近 100 条点赞，用 `batch_add_note_like_zset_and_expire.lua` 批量灌入 + 随机过期，再把本次点赞加进去。

### 第 5 步：发 MQ 顺序消息，返回成功（:879-912）

构建消息体（注意最后这个字段，简历第 4 条的伏笔）：

```java
LikeUnlikeNoteMqDTO {
    userId: 10001,          // 谁点的
    noteId: 1834567890123456,
    type: LIKE,
    createTime: now,
    noteCreatorId: 10002,   // 作者（计数时给作者加获赞数）
    eventId: UUID.randomUUID()   // 业务事件 ID：一次点赞动作生成一个，下游幂等键
}
```

发送（:895-910）：

```java
String destination = "LikeUnlikeNoteTopic:Like";      // Topic:Tag，Tag 区分点赞/取消
String hashKey = String.valueOf(userId);              // 分区键 = 用户 ID
rocketMQTemplate.asyncSendOrderly(destination, message, hashKey, callback);
```

三个知识点一次说清：

- **`Topic:Tag` 冒号语法**：一个 Topic 用 Tag 细分消息类型（Like / Unlike），消费者按 Tag 分流，不用建两个 Topic；
- **`asyncSendOrderly` = 异步 + 顺序消息**：异步是为了接口快（不等回执）；顺序的实现是——RocketMQ 一个 Topic 下有多个 Queue（队列），发送时拿 hashKey 做哈希，**同一个 userId 的消息永远进同一个 Queue，同一个 Queue 内的消息严格按发送顺序被消费**。这样张三的"点赞→取消→再点赞"三条消息不会乱序——先取消后点赞那就出鬼了；
- **发完就 `return Response.success()`**：用户看到"点赞成功"时，数据库里什么都还没发生。**同步/异步的边界就在这一行。**

### 同步段小结

用户等到"成功"时，系统只做了：校验 + Redis 位图置位 + Redis ZSet 更新 + 发 MQ。**数据库零写入**，接口耗时几毫秒。这就是"降低同步写库压力"的字面含义。

## 2. 点赞的异步段（消息的两跳）

### 第 1 跳：关系落库——LikeUnlikeNoteConsumer（note 服务）

```java
@RocketMQMessageListener(topic = "LikeUnlikeNoteTopic",
        consumeMode = ConsumeMode.ORDERLY)   // 顺序消费：单线程按 Queue 顺序拉
public class LikeUnlikeNoteConsumer implements RocketMQListener<Message> {

    private RateLimiter rateLimiter = RateLimiter.create(5000);  // 每秒 5000 令牌

    public void onMessage(Message message) {
        rateLimiter.acquire();               // 削峰：拿不到令牌就阻塞等着
        // 按 Tag 分流：Like → handleLikeNoteTagMessage ...
    }
}
```

`handleLikeNoteTagMessage`：把消息体转成 DTO → 插 `t_note_like` 关系表（user_id + note_id + status + create_time）。

**幂等兜底**：表上有 `(user_id, note_id)` 联合唯一索引 + `ON DUPLICATE KEY UPDATE`——同一条点赞消息被重复消费，insert 撞唯一索引转成 update，不会插出两条。**注意：这是我们修过的坑 ①——原表没有唯一索引，ON DUPLICATE KEY 形同虚设，2026-11-19 补上了。**

落库成功后，转发计数消息给计数服务：`CountNoteLikeTopic`，带上 noteId、noteCreatorId、**eventId 原样透传**。

`RateLimiter`（Guava，每秒 5000 令牌）是削峰闸门：上游突发 10 万点赞消息，消费者按每秒 5000 的速率匀速拉，DB 不会被瞬间打爆。

### 第 2 跳：计数——CountNoteLikeConsumer（count 服务）

两步：**先幂等判重，再进聚合器。**

**幂等判重**（`MqDedupSupport.isDuplicateByEvent`）：

```java
String redisKey = "mq:dedup:" + TOPIC + ":" + eventId;
Boolean first = redisTemplate.opsForValue().setIfAbsent(redisKey, "1", 24小时);
// 写入成功 = 首次 → 放行；key 已存在 = 重复 → 拦截，直接返回确认消费
```

- 幂等键 = **Topic + eventId**（业务事件 ID），不是 RocketMQ 的 msgId——msgId 在重试重投时会变，eventId 随消息体流转永远不变；
- Redis 异常时降级走 MySQL 唯一索引兜底（双层防线：Redis 快但可能丢数据，DB 是最终防线）；
- 判重异常时**放行**而不是拦截——宁可重复消费交给对账修正，不可漏消费。

**聚合计数**（BufferTrigger）：

```java
BufferTrigger.batchBlocking()
    .bufferSize(50000)           // 缓冲区容量
    .batchSize(1000)             // 每批最多 1000 条
    .linger(1秒)                  // 每秒聚合一次
```

攒够 1000 条或满 1 秒 → 一批消息按 noteId 分组汇总（比如这篇笔记 +37 赞）→ 一次性更新 Redis Hash `counting:note:{noteId}` 的 `like_total` 字段（1000 条消息 → 每个 noteId 一次 increment，DB/Redis 压力降一个量级）→ 再发一条 MQ（`CountNoteLike2DBTopic`）由 `CountNoteLike2DBConsumer` 把聚合计数 upsert 进 `t_note_count` 表。

**为什么计数要"先 Redis 后 DB"两段**：Redis 计数是给用户实时看的（快），DB 是持久存档（慢）。1 秒内 1000 个赞，Redis increment 37 次（按笔记分组后），DB 只写 1 次。

### 最终一致性 + 对账

至此：Redis 位图/ZSet（实时）✓、t_note_like 关系表 ✓、Redis 计数 ✓、t_note_count ✓。整条链任何一环挂了都有兜底：MQ 重试 → 幂等拦截 → 对账修正（data-align 服务 XXL-JOB 分片广播，每天比对关系表和计数表，差额修正）。

## 3. 收藏链路（同构，30 秒讲完）

`POST /note/note/collect` → `NoteServiceImpl.collectNote`。

**代码结构和点赞一模一样**，只是换了一套 key 和表：

- 判重：`note_service:rbitmap:user_note_collect:{userId}`（Roaring Bitmap，`rbitmap_note_collect_check.lua`）；

## 4. 关注链路（user-relation 服务）

`POST /relation/relation/follow`，body `{"followUserId": 10002}` → `RelationServiceImpl.follow`（:77）。

### 同步段

1. **校验**（:85-94）：不能关注自己；Feign 调 user 服务确认李四存在（`userRpcService.findById`）；
2. **Lua 判重 + 写入关注列表**（:97-114）：Redis key `relation_service:following:10001`（张三的关注列表 ZSet），执行 `follow_check_and_add.lua`：已关注 → 抛异常；ZSet 不存在 → 返回特殊码；否则 ZADD 写入；
3. **ZSet 不存在的回源**（:117-148）：和点赞同款套路——从 DB 查张三全部关注记录，批量灌入 + 随机过期，再重新执行写入脚本；
4. **发 MQ**（:152-182）：`FollowUnfollowTopic:Follow`，消息体 `{userId:10001, followUserId:10002, createTime, eventId:UUID}`，`asyncSendOrderly`，hashKey=userId。返回成功。

### 异步段：FollowUnfollowConsumer（relation 服务）

顺序消费 + RateLimiter 削峰（同点赞）。按 Tag 分流后，`handleFollowTagMessage` 做三件事：

**① 编程式事务插两张表**：

```java
transactionTemplate.execute(status -> {
    followingDOMapper.insert(...);   // t_following：张三的关注表加一行（10001 → 10002）
    fansDOMapper.insert(...);        // t_fans：李四的粉丝表加一行（10002 ← 10001）
});
```

一次关注写**两张表**（关注列表和粉丝列表分开存，查"我关注的"和"我的粉丝"各自高效），必须同事务——要么都成要么都败。幂等同样靠联合唯一索引。

**② 更新李四的粉丝列表 ZSet**：`follow_check_and_update_fans_zset.lua`（`relation_service:fans:10002`）。

**③ 转发计数消息**：`CountFollowUnfollowMqDTO{userId:10001, targetUserId:10002, type:FOLLOW, eventId:原样透传}` → 计数服务两个 Topic：`CountFollowingTopic`（张三关注数+1）、`CountFansTopic`（李四粉丝数+1）。

### 计数端：CountFansConsumer（简历第 4 条的实验现场）

就是幂等对照实验用的那个消费者：

1. **幂等判重**（:38-58）：`mq:dedup:CountFansTopic:{eventId}`，SETNX 判重；
2. **BufferTrigger 聚合**：按 targetUserId 分组，FOLLOW +1 / UNFOLLOW -1 汇总；
3. **更新 Redis Hash** `counting:user:{userId}` 的 `fans_total` 字段（注意代码细节：**key 存在才更新**，不存在说明缓存过期了，初始化交给查询侧做，这里不建）；
4. **发 MQ 落库** `CountFans2DBTopic` → `t_user_count` 表。

**实验证据**（简历"+100 vs +1"的出处）：往 CountFansTopic 重放同一 eventId 的消息 100 次——关幂等开关，fans_total +100；开开关，99 条被 SETNX 拦截，+1。文档：`docs/实验证据_幂等对照_20261014.md`。

## 6. 数据落点清单（以"张三点赞"为例）

- Redis 位图 `rbitmap:user_note_like:10001`：noteId 对应 bit 置 1（同步）
- Redis ZSet `user_note_like_zset:10001`：+1 条（同步）
- MQ：LikeUnlikeNoteTopic:Like 消息一条（同步发送，异步消费）
- MySQL `t_note_like`：+1 行（异步第 1 跳）
- Redis Hash `counting:note:1834567890123456`：like_total +1（异步第 2 跳，聚合后）
- MySQL `t_note_count`：like_total +1（异步第 3 跳）
- 对账：data-align 每日校验（兜底）

## 面试官介绍稿（40 秒）

> 互动写路径的设计核心是"同步段极轻、异步段极稳"。用户点赞时，同步只做三件事：Lua 脚本在 Redis 的 Roaring Bitmap 里原子判重并置位、更新 ZSet 点赞列表、发一条顺序消息——数据库零写入，接口毫秒级返回。异步段分两跳：关系消费者顺序消费落关系表，唯一索引兜底幂等，再转发计数消息；计数服务先用业务事件 ID 做 SETNX 幂等判重，再用 BufferTrigger 把一秒内的消息聚合成批次更新 Redis 计数，最后落 MySQL。Redis 和 DB 之间最终一致，由对账任务兜底。收藏和关注复用同一套模板。

## 深挖追问清单（含口径）

1. **为什么用 Lua？** → "查+写"两步在并发下有缝隙（双击/重试都会重复点赞）；Lua 在 Redis 里原子执行，把两步焊成一步
2. **判重为什么用 Roaring Bitmap 不用 Set？** → 一个 bit 判一个 noteId，O(1) 且内存极省；10 万点赞约 12KB。Set 存完整 ID，内存大一个量级
3. **位图缓存过期了怎么办？** → Lua 返回 -1 → 回源 DB 重建（已赞过则异步重建+拦截；未赞过则同步全量灌入+随机过期防雪崩）
4. **为什么不同步写库？** → 点赞是高频低价值写，同步写库 DB 扛不住峰值；MQ 削峰+聚合后 DB 写入量降几个量级
5. **为什么用顺序消息？hashKey 是什么？** → 点赞/取消必须有序，否则"先取消后点赞"数据错乱；hashKey=userId，同一用户的消息哈希进同一 Queue，Queue 内严格有序
6. **顺序消息会不会慢/数据倾斜？** → 顺序消费单线程拉一个 Queue，吞吐确实低于并发消费，用 RateLimiter 控速是配套的；某用户消息特别多才会倾斜，普通用户量级达不到
7. **MQ 挂了点餐还能成功吗？消息丢了怎么办？** → 发送在同步段，MQ 集群挂了发送会失败（回调只打日志是小坑）；真实丢失靠对账兜底（关系表 vs 计数表对差）
8. **消费重复了怎么办？** → 三层：关系表唯一索引（ON DUPLICATE KEY UPDATE）、计数链 SETNX+eventId 幂等、对账修正。实验：重放 100 次 +1
9. **为什么幂等键用 eventId 不用 msgId？** → msgId 重试重投会变；eventId 随一次业务动作生成、随消息体流转不变，且"取关后再关注"是新动作新 eventId，不会误拦
10. **BufferTrigger 是什么？为什么聚合？** → 内存缓冲队列，1 秒或 1000 条触发一批，按 noteId 汇总后一次更新；1000 条消息 → 几次 increment，DB/Redis 压力降量级
11. **Redis 计数和 DB 不一致怎么办？** → 最终一致设计，不一致是预期内的；data-align 的 XXL-JOB 分片广播任务每天对账修正
12. **关注为什么写两张表？** → t_following（我关注的）和 t_fans（我的粉丝）查询场景不同，分开存各自高效；两张表必须同事务
13. **收藏的布隆过滤器脚本是什么？** → lua 目录里有 bloom_* 一套早期实现，后来换成 Roaring Bitmap——布隆不能删元素、有误判，位图精确且支持删除（点赞需要支持取消）
