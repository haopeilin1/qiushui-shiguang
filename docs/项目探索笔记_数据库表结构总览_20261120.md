# 智汇社区 —— 数据库表结构总览

> 整理日期：2026-11-20
> 来源：`sql/01_schema.sql`（MySQL 单库 shiguang，13 张正式表）
> 范围说明：笔记正文存 Cassandra（kv 服务）、搜索索引存 Elasticsearch，均非 MySQL 表，不在本文。

## 一、用户域

### 1. t_user 用户表

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT | 用户 ID，主键 |
| shiguang_id | VARCHAR(20) | 拾光号 |
| password | VARCHAR(64) | 密码（Sa-Token BCrypt 加密） |
| nickname | VARCHAR(64) | 昵称 |
| avatar | VARCHAR(255) | 头像 |
| birthday | DATE | 生日 |
| background_img | VARCHAR(255) | 主页背景图 |
| phone | VARCHAR(20) | 手机号（登录账号） |
| sex | TINYINT | 0-未知 1-男 2-女 |
| status | TINYINT | 0-正常 1-禁用 |
| introduction | VARCHAR(500) | 简介 |
| create_time / update_time | DATETIME | 创建/更新时间 |
| is_deleted | TINYINT | 逻辑删除标记 |

索引：`uk_phone(phone, is_deleted)` 唯一；`idx_shiguang_id`

## 二、内容域

### 6. t_note 笔记表（元数据）

| 字段 | 类型 | 说明 |
|---|---|---|

| creator_id | BIGINT | 发布者 |

| is_top | TINYINT | 是否置顶 |

## 三、互动域（第 1 条主战场）

### 8. t_note_like 笔记点赞关系表

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT | 自增主键 |
| user_id | BIGINT | 点赞人 |
| note_id | BIGINT | 被赞笔记 |
| create_time | DATETIME | 点赞时间 |
| status | TINYINT | **1-有效点赞 0-已取消**（与 LikeUnlikeNoteTypeEnum 一致） |

索引：`uk_user_note(user_id, note_id)` **唯一**（幂等约束，支撑 insertOrUpdate）；`idx_note_id`
CRUD：
- 增：点赞用 `INSERT ... ON DUPLICATE KEY UPDATE` —— 同一人同一篇仅一行，重复赞把 status 刷回 1
- 删：取消点赞**不删行**，status 改 0（软取消，留痕）
- 查：① 对账 `count(*) WHERE status=1` 数真实赞数；② 位图重建"查用户最近赞的 100 篇"

### 9. t_note_collection 笔记收藏关系表

结构与模式同 t_note_like 完全镜像（status：1-有效收藏 0-已取消）。

| 字段 | 类型 | 说明 |
|---|---|---|

## 五、关系域

### 12. t_following 关注表（正向：我关注了谁）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT | 自增主键 |
| user_id | BIGINT | 关注者 |
| following_user_id | BIGINT | 被关注者 |
| create_time | DATETIME | 关注时间 |

索引：`uk_user_following(user_id, following_user_id)` 唯一；`idx_following_user_id`

### 13. t_fans 粉丝表（反向：谁关注了我）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT | 自增主键 |
| user_id | BIGINT | 被关注者 |
| fans_user_id | BIGINT | 关注者 |
| create_time | DATETIME | 关注时间 |

索引：`uk_user_fans(user_id, fans_user_id)` 唯一；`idx_fans_user_id`

CRUD：**双写设计** —— A 关注 B 插两行：t_following(A,B) + t_fans(B,A)；取关物理删除两行。
为什么冗余两份：关注列表查正向表快，粉丝列表查反向表快，各查各的不扫全表。

| 字段 | 类型 | 说明 |

## 八、对账临时表（动态建删，不在 schema 文件内）

`t_data_align_{业务}_temp_{yyyyMMdd}_{分片号}`，如 t_data_align_note_like_count_temp_20261119_0

- 由 `CreateTableXxlJob` 每天建、`DeleteTableXxlJob` 定期删，生命周期一天
- 白天：data-align 消费者把"今日有变更的笔记/用户 ID"记入（待办清单）
- 夜间：`NoteLikeCountShardingXxlJob` 等分片任务按清单逐个 count(*) 回源校正，边处理边删

## 九、从表结构看出的四条设计规律（面试可主动讲）

1. **逻辑删 vs 物理删有讲究**：用户、笔记逻辑删（数据资产不丢）；关注关系物理删、点赞收藏状态翻转（关系数据量大，不留尸）。
2. **唯一索引到处当幂等兜底**：点赞、收藏、关注、粉丝、公告回执、消息去重 —— 六张表同一思想："数据库约束是防重的最后一道墙"。
3. **事实表与汇总表分离**：关系表记事实、计数表记汇总；写分开、读走汇总（再叠 Redis 缓存）。
4. **正冗余换读性能**：following/fans 双写、t_note 冗余 topic_name —— 用存储换查询速度。
